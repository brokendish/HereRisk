- 関連文書: [Project Charter v0.5](../project-charter.md)、[Dataset Registry v0.1](../architecture/dataset-registry-v0.1.md)、[Data Publish v0.1](../architecture/data-publish-v0.1.md)、[AI共通作業規約](../development/ai-development-policy.md)

## 1. 目的・範囲・確定度

標高、洪水、津波、高潮、土砂災害の5機能が独立して利用する共通API契約の初期ドラフトである。全国対応を前提とし、初期の実データ検証は東京都から開始する。MVP 0の実装対象は標高APIのみ。他4機能の結果形式は将来の契約設計用であり、先行実装を要求しない。総合危険度や避難可否を判定せず、非該当も安全の保証とはしない。

状態と事実の分離、不明を非該当へ変換しないこと、責務分離、公開情報の制限を設計要件とする。以下のフィールド名・型候補・列挙値候補・JSON例はPROVISIONAL（暫定）。フィールドごとの詳細型・必須性・nullと省略の規則、HTTPステータス、APIパス・メソッドはUNDECIDED（未決定）であり、本書で正式スキーマを確定しない。文書版v0.1をそのままURLや応答のAPIバージョンに採用したとは扱わない。

## 2. 入力と内部選択

入力は緯度 `lat` と経度 `lon` とする。利用者に都道府県やデータセットの選択を要求しない。対象ハザードをどのAPI経路で指定するかは未決定。

座標は数値として解釈・検証する案とし、欠落、null、非数値、非有限値、範囲外を有効地点として処理しない。角度の十進度、latの範囲−90〜90、lonの範囲−180〜180を初期候補とするが、測地系、精度、丸め、境界値、文字列からの変換、重複パラメータ、入力エラー形式は詳細設計で確定する。latとlonを暗黙に交換しない。無効入力を `no_data` や `not_affected` に置き換えない。ブラウザの位置取得拒否は有効な座標が得られないクライアント側の状態であり、ハザードの非該当ではない。

| 担当 | 責務 |
|---|---|
| Backend API | 入力検証、呼び出し、公開用JSONの構築 |
| common / Location Resolver | 座標から都道府県等の地域を解決 |
| common / Dataset Selector | 地域・対象ハザード・Coverageから公開済み候補を選択 |
| 各Hazard Module | 選択された根拠データを用い、固有の事実を取得・評価 |
| Data Publish | 公開Registryを更新する唯一の処理。本APIは代行しない |

ResolverとSelectorは明確な契約で接続し、ハザード判定や公開管理を引き取らない。解決・選択処理の障害を「対象データなし」と解釈しない。都道府県JSONの分割単位やbboxだけで評価可能と断定せず、Coverageとデータの有効性を確認する。

## 3. 共通レスポンス候補

| フィールド候補 | 型の候補（未確定） | 意味 |
|---|---|---|
| `hazard` | string | 対象機能。elevation / flood / tsunami / storm_surge / landslideは暫定表記 |
| `location` | object | 評価対象のlat/lon。返却精度・座標系の表現は未決定 |
| `status` | string | 取得・評価の状態。区域該当性を入れない |
| `result` | ハザード別objectまたはnull | 正常に得られた固有の事実 |
| `dataset` | 公開用objectまたはnull等 | 根拠データの識別・版・出典。複数件の形は未決定 |
| `error` | 公開用objectまたはnull | 取得・評価できない理由。code / messageは暫定候補 |

基本6フィールドの必須性は未決定。例では比較しやすいよう常に6フィールドを置く。評価時点を根拠と対応付けるため `evaluated_at` を追加候補とする。必須性、配置、日時形式は未決定であり、データ基準日・取得日・公開日とは区別する。

### 3.1 statusとresultの関係

以下は意味の区別を示す暫定分類であり、列挙値の網羅的な確定ではない。

| 状態候補 | 意味 | resultの扱い |
|---|---|---|
| `success` | 有効な根拠により要求された取得・評価が成立 | 標高値、または区域該当性等の固有結果 |
| `no_data` | 正常に地域・データを確認したが、その地点を評価可能な公開データがない／Coverage外 | 成立した評価結果を返さない |
| `retrieval_failed` | 通信・I/O・処理障害等で必要情報を取得できない | 成立した評価結果を返さない |
| `indeterminate` | データは存在するが品質不足・不整合等で評価を確定できない | 成立した評価結果を返さない |

区域の `affected` / `not_affected` は `result` 内の該当性であり、`status` の代用ではない。正常な非該当は `success` と `not_affected` の組み合わせとなる。`no_data`、取得失敗、判定不能のいずれも、非該当・標高0m・浸水深0mに変換しない。

Registryが読めない場合は取得失敗候補、読めるが破損や参照不整合が判明した場合は判定不能候補とする。公開実体の欠落は未整備と同一視せず取得失敗または判定不能として区別する。欠損セル、複合障害、Resolver/Selector異常の詳細分類・優先順位・エラーコード体系は未決定だが、正常結果に変換しないことは要件とする。HTTP応答と業務上の状態の対応は別途決定する。

## 4. ハザード固有の結果候補

### 4.1 標高

`result.elevation_m` にメートル単位の標高を表現する。数値型の詳細、丸め・精度、鉛直基準、推定方法の表現は未決定。0mおよび負値は有効な値であり、欠損判定に真偽値変換を用いない。標高結果に `affected` / `not_affected` を強制しない。標高値から独自の危険度・安全判定を生成しない。

### 4.2 洪水・津波・高潮

`result.assessment` に `affected` / `not_affected`、`result.depth` に浸水深情報を保持する案とする。該当性と深さの取得可否を分離し、深さ不明から非該当を推定しない。

深さは元データの数値・範囲・階級を損なわず表す。候補は `depth.kind`、数値の `value_m`、範囲の `lower_m` / `upper_m`、階級の `category`。区間端点の包含、上限なし、単位換算、想定条件・シナリオとの対応は未決定。範囲や階級から架空の代表値を作らない。非該当時に深さ0を自動補完しない。

該当性のみ確定し深さが不明の場合の部分結果、status、null／省略表現は未決定。JSON例の `success` は必要な評価が成立したケースに限定する。

### 4.3 土砂災害

`result.assessment` と `result.zone_types` により、該当性と警戒区域・特別警戒区域等の区域種別を表現する案とする。区域種別は単一固定値に限定せず、重なりを表現可能にする。`warning_area` / `special_warning_area` は説明用候補であり、正式な列挙値・災害現象の種類・重複処理は未決定。区域種別が不明であることを非該当へ変換しない。

## 5. 根拠データ・公開境界・プライバシー

Hazard APIは公開済みDataset Registryのみを読み取り専用で参照する。Validate済み候補、作業領域、未公開の復元候補を直接利用しない。公開中にデータとメタデータの世代を混在させず、応答の根拠は実際に評価した版と一致させる。整合した参照の維持、キャッシュ無効化、旧データ参照終了の方式はPublish側の未決定事項と調整する。

Registryは内部の正本であり、そのJSONをそのまま返さない。`dataset` は許可した公開項目だけを抽出する。

| 公開候補 | Registryとの対応・注意 |
|---|---|
| `id` | datasets[].id。全国一意性・公開用識別子の方式は未決定 |
| `publication_version` | publication.version。API契約版やpipeline.versionとは異なる |
| `source` | source.providerや公開案内URL等の公開用要約。内部sourceオブジェクトの無条件転写は禁止 |
| `published_at` | publication.published_at。元データの基準日ではない |
| `data_reference_date` | 元データの基準日候補。Registry上の正式な対応先は未決定、推測で生成しない |
| `attribution` | 必要な出典・利用条件表示。具体的な構造は未決定 |

利用可能な出典・版・時点を示し、利用条件が求める表示を維持する。既存RegistryにAPI用フィールドを追加・変更するものではない。失敗時のdatasetは信頼できる識別情報だけを候補とし、不確かなメタデータを捏造しない。

内部ファイルパス、ファイル名、取得用URL・認証情報、pipelineの実行定義、管理主体、内部run_id、スタックトレース等の管理情報を公開レスポンスへ含めない。error.messageも内部例外の生文字列を転写せず、公開用説明にする。

位置情報の不要な保存・ログ記録を禁止する。アプリログだけでなくアクセスログ、プロキシ、トレース、エラー収集にlat/lonや位置を含むURL・本文が残らないようにする。クエリか本文かは未決定であり、本文なら自動的に保護されるとはみなさない。処理・応答に必要な位置の利用と永続保存を区別し、ログ用にリクエストやレスポンス全体を記録しない。必要な運用情報と位置情報の保持条件は別途レビューする。

## 6. 複数データセット・地域境界

同一地点の複数候補、都県境、行政区域の一部だけのCoverageを許容する。都道府県が決まっただけで評価可能としない。複数データセットの優先順位、集約、重複排除、相反する結果の扱い、datasetの配列化、境界上の包含規則はUNDECIDED。

先着順、最大値、最新という理由だけの選択や、非該当を優先する規則を独断で導入しない。選択・整合性を確定できないケースを正常な非該当として返さない。未解決選択の具体的な応答分類は詳細設計対象とする。複数都道府県Registryの更新途中を見せない要件を継承し、原子的切り替え方式自体は本書で決めない。

## 7. JSON例（すべて架空・暫定）

座標は説明用であり、その地点の実際の標高・災害リスクを示さない。データID、出典、日時、結果、エラーコードは架空。全例の型・null・フィールド構成は正式スキーマではない。datasetは単一根拠の場合だけを例示し、複数根拠を禁止するものではない。公開時点と評価時点を例示するが、実データの検証成功やAPI実装を意味しない。

### 7.1 正常：標高0m

```json
{
  "hazard": "elevation",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "success",
  "result": {"elevation_m": 0},
  "dataset": {"id": "example-elevation", "publication_version": "example-v1", "source": {"provider": "架空の提供主体"}, "published_at": "2026-10-01T00:00:00Z"},
  "error": null,
  "evaluated_at": "2026-10-14T00:00:00Z"
}
```

同じ正常形式で `elevation_m: -1.2` も有効。正の標高だけを正常としない。

### 7.2 正常：洪水区域に該当、数値の浸水深

```json
{
  "hazard": "flood",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "success",
  "result": {"assessment": "affected", "depth": {"kind": "value", "value_m": 1.2}},
  "dataset": {"id": "example-flood", "publication_version": "example-v1", "source": {"provider": "架空の提供主体"}},
  "error": null
}
```

津波・高潮でも該当性と深さを別々に表現する。hazardの表記を変更するだけで元データの意味・想定条件まで共通になるとは扱わない。

### 7.3 正常な非該当：評価可能な区域内で対象ポリゴンに該当しない

```json
{
  "hazard": "flood",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "success",
  "result": {"assessment": "not_affected", "depth": null},
  "dataset": {"id": "example-flood", "publication_version": "example-v1"},
  "error": null
}
```

### 7.4 データ未整備：正常に確認したが評価可能な公開データなし

```json
{
  "hazard": "elevation",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "no_data",
  "result": null,
  "dataset": null,
  "error": {"code": "example_no_coverage", "message": "この地点を評価できる公開データがありません。"}
}
```

### 7.5 取得失敗：公開データの読み取りに失敗

```json
{
  "hazard": "elevation",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "retrieval_failed",
  "result": null,
  "dataset": {"id": "example-elevation", "publication_version": "example-v1"},
  "error": {"code": "example_read_failed", "message": "評価に必要な情報を取得できませんでした。"}
}
```

### 7.6 判定不能：データの整合性を確認できない

```json
{
  "hazard": "flood",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "indeterminate",
  "result": null,
  "dataset": null,
  "error": {"code": "example_integrity_error", "message": "データの整合性を確認できず、判定できません。"}
}
```

### 7.7 正常：土砂災害の区域種別

```json
{
  "hazard": "landslide",
  "location": {"lat": 35.68, "lon": 139.76},
  "status": "success",
  "result": {"assessment": "affected", "zone_types": ["warning_area", "special_warning_area"]},
  "dataset": {"id": "example-landslide", "publication_version": "example-v1"},
  "error": null
}
```

## 8. APIバージョンと互換性

API契約は版を管理し、Registryのschema_version、publication.version、pipeline.versionとは別に識別する。パス・ヘッダー・本文のいずれで版を指定するか、採番、移行期間、廃止告知は未決定。

既存フィールドの削除・名称変更・型変更・意味変更、必須項目追加、statusの意味変更は互換性への影響を評価する。列挙値追加もクライアントによっては破壊的になるため、自動的に互換と判断しない。新旧契約の比較、依存モジュール・クライアントの影響評価、契約・回帰テスト、OWNER承認を経て移行する。未知のstatusやhazardを既定の正常・非該当へ変換しない。追加フィールドを許容する規則などは正式スキーマ策定時に決める。

## 9. 契約テストの受入条件（将来実装時）

以下は実施すべき検証であり、今回の実行結果ではない。具体的な型・HTTP対応・エラー分類が未決定の試験は、その承認後に期待値を確定する。

| ID | 入力・状況 | 受入条件 |
|---|---|---|
| C01 | 有効なlat/lon | Resolver、Selectorを通じて選択し、利用者の都道府県・dataset指定を必要としない |
| C02 | 欠落・null・非数値・非有限値・範囲外・lat/lon誤順 | 確定した入力規則に従い拒否。暗黙交換や正常なハザード結果への変換なし。両座標が有効範囲内の誤順は検出可能と保証しない |
| C03 | 標高の正値・0・負値 | 値を維持して正常結果とし、区域該当性を要求しない |
| C04 | 評価可能な区域内の該当／非該当 | 同じ正常statusの下でaffected / not_affectedを区別し、根拠の版と対応 |
| C05 | 候補なし・Coverage外 | no_data。not_affectedや0に変換しない |
| C06 | Registry・公開実体の読み取り失敗 | 取得失敗として識別し、空の正常結果やno_dataへ隠蔽しない |
| C07 | 破損・参照不整合・品質不足 | 判定不能等の承認済み異常分類を返し、正常結果を生成しない |
| C08 | ポリゴンなし・欠損セル | 評価可能性を別途確認。ポリゴンなしだけで非該当とせず、欠損を標高0や浸水深0へ変換しない |
| C09 | 洪水・津波・高潮の数値／範囲／階級 | 該当性と深さを区別し、元データの意味・単位・区間条件を保存。深さ不明を非該当としない |
| C10 | 土砂災害の単一区域・重なる区域 | 区域種別を表現し、未承認の優先順位で情報を消さない |
| C11 | 未公開候補・復元候補 | 公開Registryに登録されるまでAPI根拠にしない |
| C12 | Publish中・版更新中 | 一応答内の根拠データとメタデータが同じ公開版に対応。更新途中・削除済み参照を正常結果にしない |
| C13 | 複数候補・都県境・競合結果 | 承認された選択契約で検証。未決定の間に先着順や非該当優先で正常結果を確定しない |
| C14 | 正常・異常レスポンス全体 | 内部パス、管理情報、認証情報、例外詳細を含めず、必要な出典と評価時点を根拠に対応付ける |
| C15 | 正常・異常時のログ・トレース | 不要な座標・位置を含むURL・本文を保存しない |
| C16 | 契約変更・未知の列挙値 | 新旧互換性と回帰を検証し、未知値を正常・安全へ変換しない |
| C17 | HTTPと本文の対応 | 承認済みのHTTP対応表・必須性・null規則・型を満たす |

MVP 0では標高とそれに必要な共通契約を検証し、他4機能の実装テストは対象外としてNOT RUNを明記する。今回行うJSON例の構文確認は、API契約テスト・実データ検証・独立検証の代用ではない。

## 10. 未決定事項と既存文書との整合

| 未決定事項 | 実装前に必要な判断 |
|---|---|
| 入力契約 | 測地系、数値表現、精度、境界、入力不正の応答 |
| JSON契約 | 各フィールドの型・必須性・null／省略、hazard・status・errorの正式列挙値、評価時点の配置 |
| 通信契約 | APIパス、HTTPメソッド、HTTPステータス、API版の指定方式 |
| 結果詳細 | 標高の鉛直基準・精度、深さの範囲・階級・想定条件、区域種別、部分結果 |
| データ選択 | 複数根拠・地域境界・重複優先順位・競合・集約、datasetの単複形式 |
| 根拠情報 | 公開IDの一意性、出典形式、元データ基準日の対応、失敗時のメタデータ |
| 公開整合性 | 複数Registryの原子性、キャッシュ・参照寿命。Publish設計と調整 |
| 運用・互換性 | 位置情報の保護方式、ログ条件、版移行・廃止、未知値の扱い |

既存文書との照合では、責務・公開済みデータ限定・不明を安全としない原則・全国設計／東京検証・MVP 0標高限定について矛盾を認めなかった。Charterの「該当／非該当」は本書ではresultへ、「未整備／取得失敗／判定不能」はstatusへ分離して表現する。PublishのSUCCESS / FAILEDやRegistryのvalidation.statusとは用途が異なり、共通の列挙値へ統合しない。

元データ基準日のRegistry対応先、評価時点のAPI配置などは未決定の接続事項として報告し、既存文書を独断で修正しない。今後矛盾が判明した場合もOWNERへ報告し、関連契約を承認なしで変更しない。

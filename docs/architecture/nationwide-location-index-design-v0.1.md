## 1. 結論の要約

1. 現在は、住所・洪水・津波の各Providerが、**登録された全データを起動時にメモリへ展開**している（洪水の有効な形状383,078件とSTRtreeで354MiB、津波で26MiB）。さらに、**同じ東京のN03を4回読み込んでいる**（住所1回・洪水2ソース分・津波1回。1回目約125MiB、追加1回ごとに約31MiB）。東京だけで、住所＋洪水＋津波のピークは780MiB（1GBのコンテナ）。全国の登録には耐えない。
2. 責務を **Location Resolver（行政区域との関係）→ Source Resolver（検索するソースの選択）→ Regional Index Loader（ソースの索引から地点の候補だけを読む）→ Hazard Provider → Polygon Engine** に分ける。
3. 推奨する索引の方式は、**ソース（データセット）単位・世代単位のSQLite索引に R-tree を持たせ、地点ごとに候補の構成だけをディスクから読み、上限つきのキャッシュで再利用する**方式（第6章の方式D）。**都道府県別のファイルに分けてから全件をメモリに展開する方式は採らない**（ファイルを分けてもメモリは減らず、県境のソースを切断・重複させることになるため）。
4. **N03（行政区域）自体も、全国分をメモリに置けない**。Location Resolver も同じ方式（R-tree＋上限つきキャッシュ）で引く。
5. Polygon Engine（`validity`・`relation`）は**変更せずに使える見込み**。Loaderが地点の候補だけを `relation.ComponentIndex` に渡す。
6. 洪水の切替（Phase 4-N.6）は、Polygon Engine 移行計画の **Step 4 と1回にまとめる**（洪水を2回改修しない）。
7. 同時アクセスでは、索引・形状を**1回だけロードして共有**し（single-flight）、利用中のものは解放しない（参照数で固定）。メモリは「常駐＋キャッシュの上限＋SQLiteのキャッシュ＋検索の一時メモリの予約の枠＋断片化 ≤ プロセスの予算」の式で上から抑え、一時メモリは読む前に予約する（9.3〜9.4節。数値の既定値は計測で決める）。上限・待ちを超えたら、そのハザードを `error` にする（第14章）。
8. 上限値の項目は `conf/common/` に定義と既定値、`env/` に環境ごとの値を置き、起動時に固定する。サーバーを増強したら設定を変える（第15章）。CPUの並列は、Pythonの制約（GIL）からプロセス・インスタンスの数で増やす（第16章、未検証）。
9. 候補の県にそのハザードのソースが未登録（`missing`）の地点、一部のソースの検索に失敗した地点は、`no_match` にしない。区域がなければ `unknown`、区域があれば境界として `available`、失敗は `error`（第7章、契約案 3.4節。Location API の状態・理由の値は増やさない）。

関連する事実:

- 関東地方整備局の A31a（`A31a-25_83_10_GEOJSON.zip`、532MB）は**複数の都道府県にまたがる1つのソース**である。現在は東京の対象地域の近くのFeatureだけを索引に入れている。
- 起動時の SHA-256 の計算は、登録した原典ファイルの総量に比例する（全国では数GB〜数十GB を毎回読む）。
- `location-api` のヘルスチェックの猶予は120秒、Orchestratorの期限は1リクエスト2秒。

## 3. 全国化における構造的問題

| No | 問題 | 影響 |
|---|---|---|
| P-1 | Providerが、登録された全ソースの全形状を起動時にメモリへ展開する | 常駐メモリが登録量に比例する。東京の洪水だけで約350MiB |
| P-2 | N03を、利用者（住所・Providerの各ソース）ごとに読み込み・結合している | 同じデータの重複。全国のN03を常駐させることもできない |
| P-3 | 現在地の判定を共有しない（Orchestratorは緯度・経度だけを渡す） | 対象地域との関係の計算が重複し、Providerごとに判定が食い違う余地がある |
| P-4 | 対象地域との関係の実装が洪水と津波に重複（`_Region`） | 規則の変更が片方だけに入る危険 |
| P-5 | 洪水の正式索引に空間索引がなく、内容が登録（対象地域）に依存する | 地点ごとの読み出しができない。登録を変えると再構築が必要 |
| P-6 | 起動のたびに全原典ファイルのSHA-256を計算し直す | 起動時間が登録量に比例する |
| P-7 | ソースの登録が地域ファイルにあり、Registry・世代と結び付いていない | 公開済みの正しい世代だけを読む、という条件をコードで保証できない |
| P-8 | 都道府県単位で遅延ロードすると、1回のロード（東京の洪水で約3秒）がリクエストの期限（2秒）を超える | 「必要になったら県ごと読み込む」方式は、そのままでは使えない |
| P-9 | 登録していない隣県のN03がないと、境界の外側が「海」か「未登録の県」かを区別できない | 「区域外」と「データ未登録」を取り違える危険（Registry第6章） |
| P-10 | 同時実行の上限がない: HTTPサーバーは1接続1スレッド（`ThreadingHTTPServer`）、Orchestratorはリクエストごとに Provider数のスレッドプールを作る。全体の同時リクエスト数・同時検索数の上限がない | 数百の同時アクセスでスレッド・メモリが際限なく増えうる。過負荷時は各セクションが `timeout` になるだけで、受付の制御がない |
| P-11 | 資源の上限がコードの定数（`MAX_ITEMS`・Orchestratorの2秒・参考解析の `WORKERS` 等）で、環境ごとに変えられない | サーバーを増強しても設定で能力を広げられない |

## 4. 責務の分離と既存部品の再利用

```
lat, lon ──> A. Location Resolver ──> B. Source Resolver ──> C. Regional Index Loader ──> D. Hazard Provider ──> E. Polygon Engine
            （行政区域との関係）     （ハザードごとの検索ソース）  （ソース索引から地点の候補）    （原典の属性・提示）       （有効性・内外）
```

| 層 | 責務 | 持たない責務 | 再利用する既存部品 |
|---|---|---|---|
| A. Location Resolver | 地点と行政区域（N03）の関係: 候補の都道府県・市区町村、境界の近さ、行政区域外、未登録、判定不能。使ったN03の出典・版 | 住所の文字列（住所Providerの責務）、ソースの選択、ハザードの判定 | `n03_municipality._read_file`（読込みと検査）、`locate()` の規則（10m・`ambiguous`）、`_Region.relation` の規則（対象地域の外縁から10m） |
| B. Source Resolver | 地点で参照すべきソースの選択（ハザード種別・登録の対象地域・境界付近の取りこぼし防止）、欠落の明示 | Polygonの判定、索引の読込み、原典の評価範囲の推定 | `flood.registry`・`tsunami.registry` の登録（当面）。将来は Dataset Registry の公開済みエントリ |
| C. Regional Index Loader | 選ばれたソースの索引を開き、地点の候補の構成だけを読む。同じ索引・形状の再利用、上限、解放、世代の照合 | 内外の判定、属性の解釈 | SQLite R-tree の読み方（`common.polygon.sqlite_reader`、診断索引 `flood.diag`） |
| D. Hazard Provider | 候補を Polygon Engine に渡し、結果を原典の属性に対応付けて既存の提示契約で返す | 全国の索引のロード、対象地域の計算 | 現在の `FloodProvider`・`TsunamiProvider` の提示部分 |
| E. Polygon Engine | 有効性と正式な内外 | 都道府県判定、登録、キャッシュ、ロード | `relation.ComponentIndex`・`relate`（変更しない見込み） |

- 新しい部品は A〜C の3つだけ。D・E は既存のものを変えずに使い、提示の形は変えない。
- A は住所Providerにも使う。住所の文字列の推定（位置参照情報）は住所Providerに残す。

## 5. 現在地判定（Location Resolver）

詳細は[契約案](../api/location-resolver-contract-v0.1.md)第2章。要点:

| 場合 | Resolverの結果 | Hazard Providerの扱い（既存の状態に対応） |
|---|---|---|
| 1つの都道府県・市区町村の内側（境界から10mより遠い） | `inside`、候補の都道府県1つ | 通常の検索 |
| 市区町村の境界付近（同じ都道府県の中） | `near_boundary`、候補の市区町村が複数、都道府県は1つ | 通常の検索（都道府県の外縁ではない） |
| 都道府県の境界付近 | `near_boundary`、**候補の都道府県が複数**。1つに確定しない | 関係する全都道府県のソースを検索。対象地域の境界なら `unknown`（`service_region_boundary`）は現状どおり |
| 海岸・行政区域の外縁付近 | `near_boundary`（外縁） | 同上 |
| 海上・行政区域外（全国のN03を登録済みで、どの区域からも10mより遠い） | `outside_admin_area` | `not_available`（`outside_service_region`）。安全・区域外としない |
| 登録していない都道府県の可能性（N03が一部の都道府県だけ） | `outside_registered_area` | `not_available`（同上）。「海」と言わない |
| 行政区域データの未登録・検証失敗 | Resolverを作らない（起動しない） | 起動しない（現状の fail-closed と同じ） |
| リクエスト時の読込み失敗 | `failed` | セクションは `error`。`no_match` にしない |
| 座標の不正 | Resolverを呼ばない（Location APIの入力検証で422） | 現状どおり |

- 境界の許容距離は現行の10m（`BOUNDARY_TOLERANCE_M`）を維持する。N03の位置の精度（縮尺1/25,000相当）と10mの関係は未検証（第12章 O-3）。
- 対象地域の関係（`inside` / `boundary`）は**ソースの対象都道府県の集合の和**に対して求める（洪水の `_Region` と同じ。集合の内部の県境は境界ではない）。全体の結合形状を常駐させず、地点の周りの市区町村だけで局所的に求める（契約案 2.4節。既存の `_Region` との一致を回帰で確かめる）。

## 6. 索引ロード方式の比較

前提: **SQLiteのファイルを分けること自体はメモリを減らさない**。メモリを決めるのは、メモリに展開する形状とSTRtreeの範囲である。

| 方式 | 内容 | 常駐メモリ | 1回の検索 | 起動 | 県境・複数県のソース | Data Publishとの整合 | 評価 |
|---|---|---|---|---|---|---|---|
| A. 都道府県別SQLite＋選んだ県を全件展開 | 県ごとのファイル。必要な県をSTRtreeに展開 | 展開した県の量（東京の洪水だけで約350MiB。1GBに2県程度） | 速い（展開後） | 速いが、初回の県のロード（約3秒）が期限2秒を超える（P-8） | **県境をまたぐFeatureを分割・重複させる必要**（関東地方整備局のソース）。切断は禁止、重複は二重表示の危険 | 世代はデータセット単位なので、1つのソースが複数ファイルに分かれ、原子的な切替が難しい（Publish 第10章） | 採らない |
| B. ソース別SQLite＋全件展開 | 現状に近い | 登録量に比例（P-1） | 速い | 遅い | 問題なし | 合う | 採らない（全国で破綻） |
| C. 単一SQLite＋地域別クエリで展開 | 全国1ファイルから県の範囲を展開 | Aと同じ | Aと同じ | Aと同じ | 範囲で取るので切断は不要 | 全国1ファイルは、データセット単位の世代と合わない | 採らない |
| **D. ソース別SQLite＋R-tree で地点の候補だけ取得＋上限つきキャッシュ** | 地点の外接矩形の検索で、その地点を外接矩形に含む構成だけをWKBで読み、Polygon Engineに渡す | **上限（設定値）で固定**。SQLiteのページキャッシュ＋形状キャッシュ。登録量に比例しない | ディスクの読出し＋WKBの解析＋GEOS。大きな構成（最大354,115線分）で数ms〜数十msの見込み（**未計測**） | 形状を展開しないので速い | 範囲で取るので、ソースを県で切らない | ソース（データセット）＝ファイル＝世代で一致。切替はファイルの差し替え | **推奨** |
| E. 地域別メモリキャッシュ（県単位のSTRtreeをLRU） | Aにキャッシュの入れ替えを加える | 上限は設定できるが、1県が数百MiB単位で入れ替わる | 県境の地点で入れ替えが頻発しうる | Aと同じ（期限の問題） | Aと同じ | Aと同じ | 採らない |

推奨（方式D）の詳細:

- 索引の単位は **ソース（データセット）× 世代**。ソースが複数の都道府県にまたがっても1ファイルで、R-treeで地点の周りだけを読む。行政区域でPolygonを切らない。
- R-tree（SQLiteの `rtree`）の座標は32ビット浮動小数で、外側へ丸められる（下限は切り下げ、上限は切り上げ）。**候補は必ず真の候補を含む（取りこぼさない）**が、余分な候補を含みうる。判定保留の外接矩形の判定は、R-treeの値ではなく**本表の倍精度の外接矩形**（または形状の `bounds`）で行う（契約案 4.3節）。
- 候補の形状は `relation.ComponentIndex(candidates)` に渡して `search` する（地点ごとの小さな索引。Engineは変えない）。候補が数十件ならSTRtreeの作成は無視できる見込み（Phase 4-N.4 で計測）。必要なら、Engineに「候補の列に対する search」を加える（規則は同じ。ComponentIndex.search との同値テスト付き。Engineに地域・キャッシュの責務は加えない）。
- 大きな構成（数万〜数十万頂点）は、毎回WKBを解析すると重い。**形状キャッシュ**（頂点数またはバイト数の上限つきLRU、解析済みの形状を保持）で再利用する。上限を超える1件はキャッシュせずに処理する（上限で失敗にしない）。
- 診断索引の「塊」（chunk）方式は、正式な内外（GEOS）には使わない（Polygon Engine 契約: 正式判定は形状全体のGEOS）。
- 属性は判定後に、該当した構成の行だけを読む（洪水の現在の `_Index.rows` と同じ）。

## 7. 都道府県境界と複数ソース・3つの範囲

| 概念 | 意味 | 持ち主 | 混同してはならないこと |
|---|---|---|---|
| 原典の対象範囲（収録範囲・評価範囲） | 原典が想定・評価した範囲。A31a・A40は明示しない | 原典（Registry の `coverage`、未決定） | データの外接矩形・Polygonがないことを、評価範囲とみなさない |
| 登録した検索対象地域（service region） | HereRiskがそのソースを検索する都道府県の集合 | 登録（地域ファイル → 将来 Registry） | 検索対象であることは、評価済みであることではない |
| 行政区域（N03） | 地点がどの都道府県・市区町村に近いか | Location Resolver | 都道府県は検索候補を絞る単位で、ハザードの範囲を制限しない |

規則:

- 県境をまたぐソースを除外しない。原典のPolygonを行政境界で切断しない。複数ソースを統合しない（DP-11）。
- 境界付近では候補の都道府県をすべて残す（1つに確定しない）。
- 候補の都道府県のうち、そのハザードのソースが登録されていない県があれば、Source Resolverは**欠落（`missing`）として明示する**。欠落がある選択は `coverage: partial` で、Providerはその地点を**対象地域の境界として扱う**（`region_state: region_boundary`）。
- Location API の状態への対応（契約案 3.4節。状態・理由の値は増やさない）:

| 状況 | `status` |
|---|---|
| 選択の失敗、または選んだソースの1つでも検索が完了しない | `error`（一部のソースの結果だけを返さない） |
| 選んだソースが0件（県内にソースがない・行政区域外・登録区域外） | `not_available`（`outside_service_region`） |
| 区域がある（`missing` があっても） | `available`。見つかった区域は返す（DP-08）。`missing` があれば `region_state: region_boundary`。完全性は主張しない（`candidate_completeness: not_guaranteed`） |
| 区域がなく、`missing`・判定保留・境界上・対象地域の境界のどれか | `unknown`（`missing` は `service_region_boundary`） |
| それ以外（`missing` なし・全ソースが `inside`・全検索が完了・何も該当なし） | `no_match` |

- **保証**: `missing` がある地点、一部のソースの検索が失敗した地点は、`no_match` にならない（契約案 INV-1〜INV-3）。県境で片方の県のソースが未登録なら、区域がなければ `unknown`、区域があれば `available`（境界として）で、「該当なし」とは言わない。
- 欠落の詳細（どの県のどのハザードが未登録か）を応答に出すかは、Location APIの項目の追加になるので別途判断する（O-6）。それまでは状態だけで不完全さを表す。
- Location Resolverの判定が不完全（`failed`）なら、Source Resolverは選択を完了としない（`complete: false`）。

## 8. Data Publish・世代との整合

- 索引ファイル＝ソース（データセット）×世代。Registryの公開済みエントリが現行世代のファイルと、そのSHA-256・形式・作成時刻を指す。Loaderは**Registryが指す現行世代だけ**を開き、形式・`meta.status: complete`・SHA-256（索引ファイルの）を照合する。
- 世代の切替: 新しい世代のファイルを開いて照合 → 参照先を差し替え → 旧世代は実行中のリクエストが終わるまで開いたままにする（参照数）。Publish 7.3節の「参照中のデータを削除しない」に対応するため、Loaderは「現在参照している世代」を外から確認できるようにする。
- 起動時の検証は、原典ZIPの再計算（P-6）から、**公開時に記録した索引のSHA-256と登録の照合**に移す（原典との照合は公開処理・独立検証の責務）。移すかは O-7。
- 複数都道府県のRegistryにまたがる原子的な切替（Publish 第10章、未決定）は、ソースを1ファイルにすることで、1つのソースについては1回の差し替えで済む。都道府県別Registryの更新の整合は Publish 側の未決定事項のまま。

## 9. メモリ設計と評価方法

### 9.1 目標（案、O-1）

| 目標 | 案 |
|---|---|
| 常駐メモリ | 登録したソースの数・量に比例しない。ソースを10倍にしても、同じ地点の集合での定常RSSの増加が10%以内 |
| 上限 | Loaderの形状キャッシュ・SQLiteのページキャッシュに上限を設定できる（既定値は計測で決める） |
| 1GBのコンテナ | 住所＋洪水＋津波（東京）で、ピークRSSが現在の780MiBより下がり、600MiB以下（案） |
| 応答時間 | 1ハザードあたり p95 100ms 以下、最大1秒未満（Orchestratorの期限2秒の内側。案） |
| 失敗 | メモリ不足・索引の読込み失敗・世代の不一致は、そのセクションの `error`（`no_match` にしない）。全件メモリロードへの退避はしない |

1GBに収まることは、全国の索引での計測まで保証できない。保証できない理由: 大きな構成の形状キャッシュの必要量、同時アクセス時のSQLiteの接続ごとのキャッシュ、OSのページキャッシュの扱い（コンテナのメモリ上限への計上）が未計測。

### 9.3 メモリ予算の式（補正）

設計レビューの指摘: 当初の既定値の案では、同時検索16件×1検索の読出し上限64MiB＝1,024MiBで、プロセスの予算700MiBを超えていた。同じ形の不整合がもう1つある: 開いておく索引32×接続4本×ページキャッシュ8MiB＝1,024MiB。さらに、WKBから形状へ展開したときの増加、GEOSの準備（`prepare`）、メモリの断片化を数えていなかった。**数値の既定値の案は撤回する**（第15章）。

プロセスのメモリを、重ならない項に分けて上から抑える。

```
M_base + C_hazard + C_admin + S_sqlite + R_transient + F  ≤  B_process  ≤  L_container × r
```

| 項 | 内容 | 決め方 |
|---|---|---|
| `M_base` | 検索をしていない起動後の常駐: Python・ライブラリ・住所の位置参照情報・登録とRegistryの写し・開いた索引のハンドルの固定部分・スレッドのスタック | 計測（MB-1）。構成ごと |
| `C_hazard` | ハザードの形状キャッシュ（**展開後の形状**の推定バイト数で数える。WKBのバイト数ではない） | 設定。命中率の曲線（MB-9）で決める |
| `C_admin` | Location ResolverのN03の形状キャッシュ（ハザードと別の上限。海岸線の大きな市区町村がハザードの形状に追い出されないように） | 設定。同上 |
| `S_sqlite` | SQLiteのページキャッシュ＝**プロセス全体の接続数の上限** × 1接続のキャッシュ（索引の数×接続数ではなく、全体の接続数で抑える） | 設定と計測（MB-4） |
| `R_transient` | 実行中の検索の一時メモリの**予約の枠**（下の9.4節）。キャッシュに入っていない候補の展開、地点ごとの `ComponentIndex`、結果の辞書 | 設定。MB-2・MB-3 で下限を決める |
| `F` | 断片化・解放後も返らないメモリ（Phase 4-N.1 の計測でも、解析後に解放したメモリが RSS に残った） | 計測（MB-5） |
| `r` | コンテナの上限に対する余裕の比率 | OWNER判断（O-10） |

### 9.4 形状の展開・一時メモリ・キャッシュの管理（補正）

- **展開の倍率 `k`**: 1つの構成の展開後のメモリ ≈ `k` × WKBのバイト数（＋固定の部分）。`k` は頂点数・穴の数・`prepare` の有無で変わる。**現在の計測からは `k` を分離できない**（洪水の有効な形状とSTRtreeの354MiBには、読み出したWKBのバイト列のリストが一時的に含まれる）。MB-2 で、頂点数の区分ごと（100未満〜10万以上、東京の最大の構成 354,115線分を含む）に、`prepare` あり／なしで計測する。
- **数え方を1つにする**: 展開した形状は、必ず「キャッシュ（`C_hazard` / `C_admin` に計上）」か「そのリクエストの一時（`R_transient` の予約に計上）」のどちらかに属する。両方に数えない。数えない形状を作らない。
- **一時メモリの予約**: 1つの検索は、候補のWKBを読む**前に**、R-treeの検索と同時に各候補のWKBの長さ（`length(wkb)`）を読み、キャッシュにない候補について `k × WKBの合計 ＋ 固定の部分` を `R_transient` の枠から予約する。予約できたら読み・展開し、終わったら返す。枠が空くまでの待ちは、待ちの上限とリクエストの残り時間の短い方。待てなければ、そのハザードは `error`。
  - これにより、同時検索の数は件数の上限（`search.max_concurrent`、CPUのため）と、バイトの予約の両方で抑えられる。小さな検索は多く並び、大きな検索は少なく並ぶ。「件数×最悪の大きさ」で予算を固定しない。
  - 1つの検索の必要量が `R_transient` 全体を超える場合、その地点は常に処理できない。起動時に、各索引の最大の構成のWKB（索引に記録）について `k × 最大のWKB ≤ R_transient` を確かめ、満たさなければ起動しない（登録したデータを処理できない設定を拒否する）。地点ごとの合計の最大は索引から決められないため、MB-3 の実測で確かめ、回帰の地点で予約の不足による `error` が0件であることを受入条件にする。
- **キャッシュに入れる**: 展開した形状をキャッシュに入れるときは、予約からキャッシュへ計上を移す。キャッシュの空きは、参照数0の要素を追い出して作る。参照中（pin）の要素ばかりで空きが作れなければ、キャッシュに入れずに一時のまま使い、リクエストの終わりに捨てる（キャッシュの上限を超えない）。
- **実行中のオブジェクト**: 地点ごとの `ComponentIndex`・候補の列・結果はリクエストごとで、固定の部分として予約に含める（MB-2 で、候補数あたりの大きさを計測）。
- **`MemoryError`**: そのハザードのセクションを `error` にし、予約を返し、参照数0のキャッシュを捨てる。カーネルによる強制終了（OOM kill）はプロセス全体の停止になり、`error` に変えられない。**だから上の式で、強制終了が起きない側に予算を置く**。

### 9.5 1GBのコンテナでの既定値の決め方（補正）

既定値は推測で決めず、次の順に計測から導く（4-N.4 の受入条件）。

1. `B_process = L_container × r`（`r` は O-10。目安の候補は 0.7）。
2. `M_base`（MB-1）と `F`（MB-5）を構成ごとに計測する。
3. `R_transient` の下限 = max（`k` × 登録データの最大の構成のWKB、`k` × MB-3 の地点ごとの合計の最大）＋固定の部分。目標の同時数 `N` に対しては `R_transient ≥ max（下限、N × k × 地点ごとの合計の p95）`。
4. `S_sqlite` = 全体の接続数の上限 × 1接続のキャッシュ（MB-4）。
5. 残り = `B_process − M_base − S_sqlite − R_transient − F` を `C_hazard` と `C_admin` に分ける（MB-9 の命中率と p95 の曲線から）。
6. 残りが、意味のある命中率に必要な大きさに満たなければ、目標の同時数 `N` を下げる。それでも成り立たなければ、**その登録データは1GBでは成立しない**と記録し、必要なメモリを報告する（データを減らさない。全件メモリロードに戻さない）。
7. 決めた値で長時間の負荷試験（MB-6）を行い、ピークRSSと `memory.current` が `B_process` 以内であることを確かめる。

| No | 計測（4-N.4 の受入条件に追加） | 条件 | 合格の条件・記録 |
|---|---|---|---|
| MB-1 | `M_base` | 構成ごと（住所・洪水・津波の単独と組合せ）、別プロセス、1GBのコンテナ | 起動後・検索前のRSS |
| MB-2 | 展開の倍率 `k` と固定の部分 | 頂点数の区分ごと、`prepare` あり／なし、候補数ごとの `ComponentIndex` と結果 | `k` の区分ごとの値（最大値を設計に使う） |
| MB-3 | 地点ごとの候補のWKBの合計 | 洪水601地点・参考解析2,113組・津波の検査点9,297点・格子、N03 も | p50・p95・最大。最大の地点 |
| MB-4 | SQLiteのページキャッシュの実際の大きさ、ファイルのページキャッシュのコンテナへの計上 | `cache_size` を変える。cgroup の `memory.current`（anon と file）も記録 | 1接続あたりの増加。file の計上が強制終了につながるか |
| MB-5 | 断片化・返らないメモリ `F` | キャッシュを極小にして追い出しを繰り返す長時間の試験。`MALLOC_ARENA_MAX` 等は計測だけ（採用はしない） | 生きているデータの見積りとRSSの差 |
| MB-6 | 決めた既定値での負荷試験 | C-2・C-3 の負荷を30分以上 | ピークRSS ≤ `B_process`、強制終了なし、結果は逐次と全件一致、誤りは明示的なものだけ |
| MB-7 | 起動時の整合性検査 | 当初案（16×64MiB、32×4×8MiB）を含む不整合な設定 | 起動しない |
| MB-8 | 予約の不足 | 回帰の地点（MB-3 と同じ） | 予約の不足による `error` が0件 |
| MB-9 | キャッシュの大きさと命中率・応答時間 | `C_hazard`・`C_admin` を変える | 曲線。既定値の根拠 |

### 9.2 評価方法

| No | 計測 | 条件 | 記録 |
|---|---|---|---|
| M-1 | 構成ごとのRSS | 別プロセス、メモリ上限1GBのコンテナ。住所・洪水・津波の単独と組合せ | 起動後・定常（601地点＋津波2,000地点の後）・ピーク |

## 10. Location APIとの接続（既存契約は変えない）

- Orchestratorに Location Resolver を1つ持たせ、1リクエストで1回だけ解決し、結果（`ResolvedLocation`）を各Providerに渡す。Providerの `lookup(lat, lon)` は残し、`lookup(lat, lon, location=...)` を追加の任意引数にする（受け取らないProviderは従来どおり）。
- Resolverの失敗は、Resolverを使うセクションだけを `error` にする（他のセクションに波及させない。現在のOrchestratorの方針と同じ）。
- 応答のJSONは変えない（`service_region_relation`・`region_state` などは同じ規則で計算されるだけ）。

## 14. 同時アクセス（設計要件）

前提: 単一プロセス・複数スレッド（現在の `ThreadingHTTPServer`＋Orchestratorのスレッド）。数十〜数百の同時アクセスは**未検証**であり、本章は性能の保証ではない。

| 要件 | 設計 | 既存の前例 |
|---|---|---|
| 複数地域への同時検索 | 地点ごとに Source Resolver が選んだソースの索引だけを読む。索引のハンドルはソース×世代ごとに1つで、スレッドから共有する。SQLiteの接続はハンドルごとの小さなプール（`connections_per_index`）から借りる | 参考解析APIの接続プール（`WORKERS`・`ACQUIRE_TIMEOUT_S`） |
| 同じ地域への同時検索 | 形状キャッシュは共有。同じ構成の解析が同時に要求されたら、1つのスレッドだけが読み・解析し、他は完了を待つ（**single-flight**、待ちは期限つき） | — |
| 同一索引の重複ロード防止 | 索引のハンドルの作成（ファイルを開く・meta と世代の照合）も single-flight。ハンドルの表は鍵で守る | — |
| 利用中索引の解放防止 | ハンドル・キャッシュの要素は**参照数**を持ち、検索の間は参照を保持する（pin）。解放・追い出しは参照数0のものだけ。追い出された後も、参照を持つスレッドは自分の参照で処理を終えられる | Publish 7.3節（参照中のデータを削除しない） |
| メモリ不足時の安全な処理 | 9.3〜9.4節の式で上から抑える: `M_base + C_hazard + C_admin + S_sqlite + R_transient + F ≤ B_process`。起動時に設定がこの式を満たさなければ起動しない。検索の一時メモリは読む前に予約し、予約できなければ待ち、待てなければ `error`。`MemoryError` はそのセクションの `error`、参照数0のキャッシュを捨てる。全件メモリロードへ退避しない | Polygon Engine の `limit_exceeded`（一部を返さない） |
| ロード待ち・タイムアウト | 同時検索数の上限（セマフォ）、同時ロード数の上限、待ちの上限は、そのリクエストの残り時間（Orchestratorの期限）を超えない。超えたら、そのハザードのセクションを `error`（`timeout`、O-11）。待ちの間に部分的な結果を返さない | Orchestrator の期限（2秒）、参考解析の `busy` |
| リクエスト間のデータ混在防止 | 共有するのは**不変のもの**だけ（解析済みの形状、索引のハンドル、読取専用の接続）。地点ごとの `ComponentIndex`・候補の列・結果の辞書はリクエストごとに作る。リクエストは開始時に各ソースの世代を1つ固定し、その世代のハンドルだけを使う。キャッシュの鍵に世代を含める。GEOSの `prepare` は共有形状に対して、キャッシュに入れる前に1回だけ行う（共有後に変更しない） | 現在の各Providerは地点ごとに結果を新しく作る |

## 15. リソース管理（設定）

配置（基本アーキテクチャ 第6章・Charter P7）:

- 項目の**定義・型・範囲・既定値**は `conf/common/`（Location API と各Hazard Providerが共有する資源の設定。例 `conf/common/location-resources.json` と Schema。**今回は作らない**）。
- **環境ごとの値**（開発Mac・VPS・増強サーバー）は `env/`。実環境のファイルはGitで追跡せず、サンプルだけを追跡する。
- 読込み・検証は共通 Configuration Manager。**起動時に解決して固定する**（基本アーキテクチャ 6.2節: 実行中に設定を変えない）。一般APIのリクエストで上書きしない。Data Manager による運用変更の可否は未決定のまま。

**数値の既定値は決めない**（当初の案は 9.3節の不整合のため撤回）。9.5節の手順と MB-1〜MB-9 の計測で決め、OWNER が承認する（O-10）。

| 項目（案） | 意味 | 予算の式の項 |
|---|---|---|
| `memory.container_limit_bytes` | コンテナのメモリ上限（`env/`。Compose の `mem_limit` と一致させる） | `L_container` |
| `memory.headroom_ratio` | 余裕の比率 | `r` |
| `memory.process_budget_bytes` | プロセスの予算（`L × r` 以下）。起動時の整合性検査に使う | `B_process` |
| `loader.geometry_cache_bytes` | ハザードの形状キャッシュの上限（展開後の推定バイト数） | `C_hazard` |
| `resolver.geometry_cache_bytes` | N03の形状キャッシュの上限 | `C_admin` |
| `loader.max_connections` | プロセス全体のSQLiteの接続数の上限（索引ごとの接続はこの中から借りる） | `S_sqlite` |
| `loader.sqlite_cache_kib` | 1接続のページキャッシュ | `S_sqlite` |
| `search.transient_budget_bytes` | 検索の一時メモリの予約の枠 | `R_transient` |
| `search.expansion_factor` | 予約に使う展開の倍率 `k`（MB-2 の最大値。計測した値より小さくしない） | — |
| `search.max_concurrent` | 同時検索数の上限（CPUのため。メモリは予約で抑える） | — |
| `search.acquire_wait_s` | 同時検索の枠・予約の待ちの上限（リクエストの残り時間を超えない） | — |
| `loader.max_open_indexes` | 開いておく索引のハンドルの数（ハンドルの固定部分は `M_base` に計上） | `M_base` |
| `loader.max_concurrent_opens` | 同時ロード数 | — |
| `loader.open_wait_s` | ロード待ちの上限 | — |
| `loader.idle_close_s` | 参照数0のハンドルを閉じるまでの時間 | — |
| `loader.eviction` | 追い出しの方針（当面は `lru` だけ） | — |
| `request.timeout_s` | Orchestratorの期限。2.0（**Location API 第7章の値。変えるのは契約の変更**） | — |

- 起動時の整合性検査（MB-7）: 上の式を満たさない、`k × 最大の構成のWKB > R_transient`、`acquire_wait_s ≥ request.timeout_s` のどれかなら起動しない。
- 応答の上限（`MAX_ITEMS` 500）は提示契約の値で、資源の設定にしない（環境で答えの形を変えない）。
- 必要な索引をロードできない場合: 登録がない → `not_available`（現状どおり）、登録はあるが開けない・待ちの超過・上限 → `error`。判定結果を作らない。

## 16. スケールアウト

| 要件 | 設計 |
|---|---|
| ローカルのキャッシュに正本を持たせない | キャッシュは索引ファイルから作り直せるものだけ。捨てても結果は変わらない（IL-4） |
| 索引の正本は永続ストレージ | 索引ファイル（ソース×世代、不変）と Registry が正本。インスタンスは読取専用でマウントして読む（現在の Compose の volume と同じ考え方） |
| 公開世代を読む | 各インスタンスは Registry の現行世代を読み、照合したファイルだけを開く |
| インスタンスごとの独立キャッシュ | キャッシュ・ハンドル・接続はプロセス内だけ。インスタンス間で共有しない（OSのページキャッシュは同じサーバー上なら共有される） |
| 世代切替と検索中の整合性 | 1つのリクエストの中では、各ソースについて1つの世代だけを使う（14章）。インスタンスごとに切替の時刻がずれるため、切替中はインスタンスによって新旧の答えがありうる。旧世代の削除は、全インスタンスが参照を終えてから（判定方式は未決定、O-12）。どの世代の答えかを追跡できるよう、世代を応答に出すかは O-13 |
| 分散のためだけの部品を足さない | Redis 等の共有キャッシュ・分散ロックは追加しない。インスタンスは互いに通信しない |
| 能力の増やし方 | CPUの並列はプロセス・インスタンスの数で増やす（PythonのGILのため、1プロセスのスレッドだけでは増えない見込み。GEOSの処理がGILを外すかは**未検証**）。メモリは設定（キャッシュ上限・同時検索数）で増やす。ストレージは索引ファイルの追加だけ |

API契約: 応答の形はインスタンスの数に依存しない（各インスタンスが同じ規則で同じ世代から答える）。インスタンスの数を増やすことに、Location API の契約の変更は要らない見込み（世代の表示を足すかは O-13）。

区分: **実装済み**＝現在のコードにある、**設計上対応**＝本書で方式を定めたが未実装、**未検証**＝計測・試験をしていない。

| No | 観点 | 実装済み | 設計上対応 | 未検証 | 検証方法（実装段階） |
|---|---|---|---|---|---|
| C-1 | 登録地域数が増えても、起動時メモリが全Polygon数に比例しないか | なし（**現状は比例する**: P-1） | 方式D（形状を起動時に展開しない）、Location ResolverのN03も索引から読む | 全国規模の索引での起動時・定常のRSS | M-2（登録量1・5・10倍） |

| C-4 | キャッシュ解放中に検索結果が壊れないか | — | 参照数による固定、不変の共有物、参照数0だけを追い出す | 追い出しと検索の競合 | キャッシュ上限を極小にして同時に検索し、全件メモリの結果と全件一致 |

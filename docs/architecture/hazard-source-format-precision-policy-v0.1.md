## 1. OWNERの方針［確定］

1. 標準的で広く利用され、実データの品質に問題の少ない形式を優先する。
2. 小数10桁以上の座標は、検索用データでの丸めを許容する。
3. GMLの参照不整合を、原典の無断修正によって解決しない。

## 2. 範囲

対象: 津波 A40、高潮 A49、土砂災害 A33、行政区域 N03（2026年版）。洪水 A31a は既存の契約を維持し、本書の影響だけを評価する（第6章）。ハザード固有の意味・区分・属性は共通化しない（ADR-001）。

## 3. 入力形式の採用方針［提案］

### 3.1 判定の基準

**GeoJSONを第一候補とする。ただし、形式名だけで一律に選ばない。** 入力ごとに次のすべてを確認し、結果を記録する（第7章 FP-1）。

| No | 基準 | 確認方法 |
|---|---|---|
| FC-1 | 公式配布物である | 取得元台帳の配布ページ・取得記録（ZIPのSHA-256）。ZIP内の該当メンバーであること |
| FC-2 | Featureと属性を保持している | 件数・属性名・型・値。可能な場合、同じZIP内の別形式（GML・Shapefile）と属性を全件照合する |
| FC-3 | Polygon・MultiPolygon・穴を保持している | 環の数・部分の数。可能な場合、別形式と照合する |
| FC-4 | 座標参照系と軸の順序が明示されている | 第3.2節 |
| FC-5 | 座標の精度が分かる | 小数の桁数の分布。第4章の精度の規則の適用範囲内であること |
| FC-6 | 原典との対応を追跡できる | 出現順のFeatureの対応、`record_key`（N 第4.3節） |
| FC-7 | 不正データを検出できる | 構文・重複キー・非有限値・構造の破損・参照の破損を検出できる形式であること |
| FC-8 | 全国の配布データへ拡張できる | 同じ形式が他の都道府県でも配布されていること（データページの表記） |

- GMLとGeoJSONが一致しない場合は、理由を確認して記録する（第5章、検討記録 第2章）。
- 採用した形式・使わなかった形式とその理由を、設定スナップショットとNormalize Recordに記録する（第8章）。

### 3.2 座標参照系（GeoJSON）

- **GeoJSONがRFC 7946の座標参照系の条件（WGS84の経度・緯度、`crs` メンバーなし）に準拠するとは推定しない。** 国土数値情報のGeoJSONは `crs` メンバーでJGD2011（`EPSG:6668`、`urn:ogc:def:crs:EPSG::6668`）を宣言している［実測: A40・A49・A33・N03 2026］。
- 座標参照系は、Source Definitionの設定でデータソースごとに明示する（例: `EPSG:6668`、軸の順序 経度・緯度）。Normalizeは、ファイルの `crs` メンバーがその設定と一致することを検証する。欠落・不一致・未知の表記は拒否する（推定で補わない）。
- 座標系の変換は行わない（N 第6.4節）。API入力（WGS84想定）との関係は未決定のまま（N ON-11）。

## 4. 座標精度・丸め方式［提案］

### 4.1 2つの表現の区別

| 表現 | 内容 | 用途 |
|---|---|---|
| 原典の座標 | 公式ZIP内の数値トークン（文字列）そのもの。**ZIPを変更しない** | 来歴・追跡・再計算 |
| 検索用の正規化座標 | 第4.2節の規則で小数8桁に丸めた値を、10⁻⁹度単位の整数（10の倍数）で表したもの | RTree・点の内外判定・妥当性の評価（丸め後）・Integration |

- **丸め後の形状は検索用の派生表現であり、原典と同一であると偽らない。** Normalize成果物・Recordに、精度の規則（第4.2節）の識別子・版と、丸めの統計（第4.4節）を必ず記録する。
- これは、N 第10章の「派生ジオメトリ」（無効形状の修復）とは別の概念である。用語は「**精度の正規化（precision normalization）**」とする。精度の正規化では、頂点を追加・削除せず、頂点の順序・環・部分の構成を変えない。

### 4.2 丸めの規則（精度プロファイル `coord-precision-round8-v1`）

1. 座標の数値トークンを、浮動小数を経由せず、十進の文字列から `Decimal` に変換する（Python の `float` に変換しない）。
2. 指数表記・非有限値・符号以外の文字を含むトークンは拒否する（N 第5章と同じ）。
3. 小数の桁数の上限を **17桁** とする（倍精度の浮動小数の表現から生成されたトークンを受け付けるため）。18桁以上は拒否する［提案。値はOWNER判断］。
4. 小数8桁に量子化する。**中間値（9桁目以降がちょうど5）は0から遠い方向へ丸める**（`ROUND_HALF_UP`。正の値は切り上げ、負の値は絶対値で切り上げ）。負の値も絶対値で対称に扱う。
5. 小数8桁以下のトークンは値を変えない。
6. 結果を10⁻⁹度単位の整数（10の倍数）にする。範囲・形式の規則は、N 第6.3節の初期座標プロファイルに従う。

- 規則は決定的である。同じトークンからは、常に同じ整数を得る。
- 丸めによる各座標の変位は、規則により **5×10⁻⁹度以下** である（例: 東京付近で約0.5mm）。
- 公式GMLの8桁の値は、浮動小数の表現で丸められたとみられ、中間値で本規則と一致しない場合がある（N03 2026年版で約5.2%の値。検討記録 第2章）。**本規則の結果を、公式GMLの値と同一であるとは扱わない。**

### 4.3 追跡可能性

- Featureごとに、原典の座標トークンの列の正規化表現のSHA-256（`source_coordinate_tokens_sha256`）を記録する。トークンは出現順に並べ、文字列のまま扱う。
- 頂点の対応は、（`record_key`, `polygon_index`, 環の番号, 頂点の番号）で一意に決まる（頂点を削除しないため）。
- Source Fidelity Validateは、原典ZIPから独立にトークンを読み、第4.2節の規則を再適用する。その結果が正規化座標と全件一致すること、`source_coordinate_tokens_sha256` が一致することを検証する（第6章 ND-4）。

### 4.4 丸めの影響の検証（Rounding Check）

Normalize（または独立した検証工程）で、全Polygonについて次を検証し、統計を記録する。

| No | 検証 | 不成立の扱い |
|---|---|---|
| RC-1 | 頂点数・環の数・部分の数が、丸めの前後で同じ | 停止 |
| RC-2 | 環の閉包（始点＝終点）が保たれる | 停止 |
| RC-3 | 丸めで、**新たに**連続する同一座標の頂点が生じない | 停止（原典に元からある連続重複は、N ON-6どおり記録する） |
| RC-4 | 丸めで、環が縮退しない（異なる点が3未満、または面積が0） | 停止 |
| RC-5 | 丸めで、環の向き（符号付き面積の符号）が変わらない | 停止 |
| RC-6 | 原典の精度での妥当性の状態・分類と、丸め後の妥当性の状態・分類が一致する（新たな自己接触・自己交差・穴と外周の接触・穴の配置の変化がない） | 停止 |
| RC-7 | 各座標の変位が5×10⁻⁹度以下 | 停止（規則上は起きない。実装の誤りの検出） |

- **停止**とは、そのデータソースの取込み（Normalize）を **BLOCKED** とし、手動の確認を求めることである。**不成立のFeatureだけを除外して成功とはしない。自動で別の規則を採用しない。**
- 停止したFeatureの位置（`record_key`・`polygon_index`・環・頂点）と原因を記録する。
- RC-6の原典の精度での評価は、整数の参照判定器で、10⁻¹⁷度単位の整数として厳密に行う。GEOS（倍精度）は15桁以上の精度を厳密には表せないため、RC-6の判定には単独で使わない［提案］。
- 小数8桁が不十分な例（RC-3〜RC-6の不成立）が見つかった場合は、その件数・位置・原因と、代替案を報告する。代替案は次のとおり（いずれもOWNER判断）。
  - (a) 9桁への丸め
  - (b) そのデータソースは別形式を採用する
  - (c) 取込みを保留する

### 4.5 RTree・点の内外判定との接続

RTree・点の内外判定・Integrationの地域の選別・unknownの外接矩形は、**すべて検索用の正規化座標（同じ整数のモデル）**を使う（I 第6.3節）。原典の座標と検索用の座標を混在させない。

## 5. GML参照不整合の扱い［提案］

- 原典のGMLを改変しない。**参照文字列の自動補正（大文字・小文字の無視、下線の除去など）を標準の動作にしない**（OWNERの方針3）。
- 参照不整合は、検証結果として記録する（Normalize Record・取得元台帳の形式の評価）。記録する項目は、件数・型（例: 大文字・小文字の違いだけ、下線の違い）・例である。
- GMLが利用できなくても、同じZIP内の**公式GeoJSONが独立に検証できれば**、GeoJSONを採用候補にできる。
- 採用したGeoJSONの検証（FC-1〜FC-8、RC-1〜RC-7、Source Fidelity Validate）が失敗した場合は、そのデータソースの取込みを **FAILED/BLOCKED** とする。GMLへの自動の切替えはしない（GMLも不整合のため）。
- 不正な区域の一部だけを、無断で除外して成功とはしない。
- **不整合のあるGMLと、利用できるGeoJSONの状態を混同しない。** 取得元台帳・Data Managerでは、形式ごとに状態を表示する（第8章）。
- 独立の照合の候補: GMLの参照が健全なデータ（A40）は、丸めたGeoJSONとGMLの全件照合を、Source Fidelity Validateの追加の検証に使える。参照が壊れたデータ（A49・N03 2026）は、同じZIP内の公式Shapefileとの照合が候補になる（**未試験**。属性・環の数の照合ができるかは実データPoCで確認する）。

## 8. Pipeline・Data Managerへの接続［提案］

工程の責務（Download → Normalize → Source Fidelity Validate → Geometry Validity Assessment → Integration → Integrated Validate → Publication Readiness → Data Publish）は変えない。

**設定スナップショット・Recordに紐付ける項目**:

| 項目 | 記録先 |
|---|---|
| 採用した入力形式（ZIPメンバー名・形式） | Source Definition（設定）、Normalize Record |
| 使わなかった形式と理由（例: GMLの参照不整合の件数） | Normalize Record（形式の評価）、取得元台帳 |
| 座標参照系の設定と、ファイルの `crs` メンバーの照合結果 | Normalize Record |
| 精度プロファイルの識別子・版、変換の実装の版 | 設定スナップショット、Normalize Record、`content.json` |

## 1. 背景と目的

OnHighGround2で複数の公式防災データを扱う中で、**同じ地点でも、公表主体や想定条件によって結果が異なる**ことが明らかになった［確定］。一つの結果だけを利用者に示すと、他の公式情報の存在や差異が伝わらず、誤解につながる可能性がある［確定］。

HereRiskは、複数の公式情報を独断で統合・順位付けして唯一の正解を決めるのではなく、各情報の出典と前提条件を保持して提示する［確定］。**利用者にデータの正当性を判定させることは目的としない**［確定］。

本書は、この基本理念を、すべてのAPI個別契約より上位の設計原則として定める。

## 2. 最上位原則［確定］

> **公式情報の違いを隠さない。**
>
> **内部は厳密に。外部はシンプルに。不確実性は隠さない。**

## 3. 規範

各原則の原則文は［確定］（OWNER決定）である。「適用」は、既存の契約・設計案での現在の対応を示す［提案］。

### DP-01 原典尊重

**原則**［確定］: 公式データの原典、属性、来歴、想定条件を保持する。正規化・地点判定によって生じた結果は原典と区別する。

**適用**［提案］: 原典の完全保持と、原典忠実性の検証・妥当性の評価・派生形状の分離（Flood Normalize契約 第1.4節 P-1〜P-6・第4.5節）。原典属性・来歴の統合成果物への保持（Flood Integration契約 第5章・第6.2節）。

### DP-02 複数結果の独立性

**原則**［確定］: 異なる公式データの結果を独立して扱う。明確に定義・承認された処理を除き、複数の結果から独自の唯一の正解を生成しない。

**適用**［提案］: ソースごとの独立した地点判定と、ソース間の浸水深の自動統合の禁止（Flood Source Selection契約 SS-7・第5章）。形状だけを根拠とした重複排除の禁止（Flood Integration契約 第5章）。同一ソース内の集約は「明確に定義・承認された処理」の候補であり、承認されるまで提案である（同 第5.3節）。

### DP-03 情報の網羅的提示

**原則**［確定］: 公開対象として採用したデータに複数の結果があれば、原則としてすべて提示・参照可能とする。未登録・未収録の公表データまで網羅しているとは主張しない。

**適用**［提案］: 全ソース・全該当・全unknownの返却と、切捨ての禁止（Flood API MVP契約 第5.4節）。目録の所属の完全性（Flood Source Selection契約 第3.4節）。候補の列挙範囲と `candidate_completeness = not_guaranteed`（同 第4.2節）。

### DP-04 非恣意的な表示

**原則**［確定］: 特定の公表主体を信頼性の順位によって自動優先しない。初期表示は全登録ソースのoverviewを基本とする。表示順、フィルター、主表示の選択を、データの正誤判定と混同しない。

**適用**［提案］: 提供主体の自動優先順位の廃止と `overview` の既定化（Flood Source Selection契約 SS-1・SS-2・SS-4・第6章）。表示順は信頼性の順位ではない（同 第8.1節）。Phase 2-B.9の [Source Priority契約](flood-source-priority-contract-v0.1.md) は、本原則と異なる方式（自動優先）であり、置き換え済みの設計案（履歴資料）として扱う。

### DP-05 違いの理解を支援

**原則**［確定］: 出典、提供主体、対象河川、想定シナリオ、作成時期、評価条件など、原典から確認できる情報を関連付ける。異なる結果について、根拠がない原因説明を生成しない。「結果が異なる」という事実と「なぜ異なるか」という解釈を区別する。

**適用**［提案］: Source Catalogの公表元・対象河川・シナリオ・版・出典（Flood Source Selection契約 第3.3節）。結果の違いの原因を推測する項目は、現在のどの契約にも定めていない。今後、原因の説明を加える場合は、原典で確認できる根拠への参照を必須とする。

### DP-06 利用者に正当性判定を強制しない

**原則**［確定］: 利用者は河川別、提供主体別、個別データソース別などの視点で情報を確認できる。これらは情報を理解するための操作であり、利用者が一つの公式データを正解と認定する操作ではない。

**適用**［提案］: ソースの選択は表示の指定であり、判定を変えず、正確さの確認を意味しない（Flood Source Selection契約 SS-3・第6.4節）。`selected_result_is_exclusive = false`（Flood API MVP契約 第5.6節）。河川別の視点は、`source_id` の粒度とあわせて未決定である（第6章）。

### DP-07 不確実性の明示

**原則**［確定］: unknown、評価範囲不明、比較不能、未収録、公開対象外、取得失敗を区別する。これらを「浸水なし」「安全」「危険なし」に変換しない。

**適用**［提案］: 状態の区別。具体的には、ソースの事実と `assessment_status`（Flood Source Selection契約 第5.2節）、5つの区別（同 第4.1節）、比較不能の `null`（同 第7章）、`no_data`・`retrieval_failed`・`indeterminate`（Flood API MVP契約 第6章）。プロジェクト定義書 P5「不明を安全と判定しない」・第7章「非該当は安全を意味しない」と整合する。

### DP-08 安全上の情報の保持

**原則**［確定］: 利用者が絞り込みや選択を行っても、他のソースに確認済みの深い浸水想定やunknownが存在する事実を隠さない。表示の簡略化によって、安全上の重要情報を欠落させない。

**適用**［提案］: `deeper_in_other_sources` の三値判定、`has_unknown_in_other_sources`、`single_source` での全ソースの返却（Flood Source Selection契約 第7章、Flood API MVP契約 第5.6節）。原則文は洪水を例にしているが、他のハザード（津波・高潮・土砂災害等）にも同じ趣旨で適用する。

### DP-09 責務分離

**原則**［確定］: Source Discovery、Point Assessment、Source Selection、API、UIを分離する。データの登録・評価・選択・表示を、単一の巨大な判定ロジックに統合しない。

**適用**［提案］: Flood Source Selection契約 第1章の責務の表。プロジェクト定義書 P1（UNIX哲学）・P2（疎結合）と整合する。

### DP-10 検証可能性

**原則**［確定］: 原典・判定結果・公開世代・設定・来歴を追跡可能にする。結果の完全性・整合性を検証できる契約を定義する。

**適用**［提案］: 内容ハッシュと実行証跡、Recordの一方向の確定順序（Flood Normalize契約 第11章、Flood Integration契約 第7章）。公開世代への設定の固定と目録の照合（Flood Source Selection契約 第3.4節・第8章）。プロジェクト定義書 P4（独立検証）と整合する。

## 4. 契約上の位置付け［確定］

- 本書は、HereRiskの**共通設計における最上位文書**とする。
- 共通API契約と各ハザードの個別契約は、本書と整合しなければならない。
- **本書だけを根拠に、既存のセキュリティ・利用条件・公開認可・データ検証の禁止事項を緩和してはならない。** 例えば、DP-03（網羅的提示）を理由に、利用条件が未解決のデータ、公開認可のないデータ、検証に合格していないデータを提示しない。
- 矛盾を発見した場合は、既存契約を無断で変更しない。対象の条項・影響・改訂案を記録して、OWNERの判断を求める。

**プロジェクト定義書との関係**［提案］: プロジェクト定義書は、プロジェクトの目的・範囲・開発基本原則（P1〜P11）を定める文書である。本書は、その下で、設計文書（アーキテクチャ・API・パイプラインの契約）の最上位に位置付ける案とする。両者の間の緊張点は第5章に記録した。本書とプロジェクト定義書の上下関係の正式な決定は、OWNER判断とする（DP-U1）。

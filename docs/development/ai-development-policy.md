# HereRisk AI共通作業規約

**Status:** Draft（OWNER承認待ち）

**Date:** 2026-10-12

**基準文書:** [Project Charter v0.5](../project-charter.md)

本規約はHereRiskにおけるAI作業に適用する。サービス定義・開発原則および担当の責務はProject Charterに従う。

## 開発体制

| 担当 | 責務 |
|---|---|
| OWNER | 構想・設計判断・最終承認 |
| ChatGPT | 要件定義・アーキテクチャ設計・作業指示・レビュー |
| Claude | 実装・修正・単体テスト |
| Codex | 独立検証・設計レビュー・指定された環境整備 |

人間とChatGPTは設計・判断・受入条件の策定を中心とし、ファイル編集・実装・検証などの実作業は原則としてAIが行う。人間による手作業は緊急時またはAIで対応できない場合に限定する。

## 1. 基本ワークフロー

原則として次の順番を守る。

1. ChatGPTによる要件・設計・受入条件の定義
2. 設計レビュー
3. OWNERによる実装方針承認
4. Claudeによる限定範囲の実装
5. Claudeによる単体テスト
6. Codexによる独立検証
7. OWNERが許可した範囲でGitHub共有（commit・push）
8. ChatGPTによる成果物レビュー
9. OWNERによる最終承認・受入判定
10. 次工程への移行

公開前に秘密情報チェックを必須とする。共有許可は最終受入承認や本番デプロイ承認とは区別する。

環境整備や文書更新などはCodexを実作業担当に指定できる。

その場合、Codex自身の作業確認と、別担当による独立検証は同一視しない。

## 2. 指示書の必須項目

AIへの指示書には原則として以下を記載する。

- 作業目的
- 対象ファイル・ディレクトリ
- 変更可能範囲
- 変更禁止事項
- 契約・仕様と既存仕様との整合条件
- テスト・検証条件
- 完了条件
- 報告書の保存先

## 3. 実装・修正ルール

- UNIX哲学を守り、一つのモジュールは一つの責務に集中する。
- APIとデータ契約を優先する。
- 共通処理は責務と契約を明確にしたうえで `common` へ集約する。
- データ欠損・取得失敗・危険区域外を混同しない。
- 重複する共通処理は適切に共通化する。
- `common` を巨大な万能モジュールにしない。
- 不要になったロジック・分岐・ファイル・設定は削除する。
- 「使用されないから残してよい」という判断は禁止する。
- 削除時は参照関係とテストへの影響を確認する。
- 設定や定数を複数の場所へ分散させない。
- 新規ディレクトリや新しい設定配置が必要な場合は理由を明示し、OWNER承認を得る。
- 既存コードの大規模な書き換えを独断で行わない。
- OnHighGround2からのコードコピーを前提としない。

## 4. 作業範囲の制御

- 指定された作業範囲外を変更しない。
- 無関係なリファクタリングを実施しない。
- 動作不良の隠蔽をしない。
- テスト失敗を成功扱いしない。
- 実行できなかった検証は未実施として報告する。
- 修正のために既存の安全対策を弱めない。
- 必要な仕様変更はOWNERへ判断を求める。

## 5. 設定ファイル管理

- 共通設定は `conf/` に集約する。
- 環境別設定は `env/` に集約する。
- 共通設定の読み込み・検証は `common` の責務とする。
- ソースコードに設定値を重複して埋め込まない。
- API契約を構成する型・列挙値などは実行時設定値と区別する。
- 機密情報はGit管理対象にしない。

## 6. テスト・検証

- モジュール単独で検証可能な構造を維持する。
- API契約テストを重視する。
- 正常系・異常系・データ欠損を検証する。
- 修正時には影響範囲を明示する。
- 実装担当とは独立した検証を原則とする。
- 検証結果はPASS、PASS WITH FINDINGS、FAIL、BLOCKEDなど、判定基準とともに明示する。

| 判定 | 基準 |
|---|---|
| PASS | 対象の検証を実施し、受入条件をすべて満たす |
| PASS WITH FINDINGS | 受入条件を満たすが、非阻害の指摘や後続課題がある |
| FAIL | 実施した検証で受入条件への不適合を確認した |
| BLOCKED | 前提条件や権限などの不足により、必要な検証を完了できない |
| NOT RUN | 対象外などの理由で検証を実施していない。理由を併記する |

自己確認か独立検証かを明示し、未実施の検証をPASSに含めない。

### 共通処理の追加・変更・削除時の検証条件

- 変更対象と依存モジュールを特定する。
- 既存の責務とAPI契約への影響を評価する。
- 影響する既存機能の回帰テストを実施する。
- 必要な検証が未実施の場合、PASSと判定しない。
- 破壊的な契約変更はOWNERの事前承認を必要とする。

## 7. AI詳細報告書

AIは作業完了後、指定された場所へ報告書を作成する。

報告書には以下を含める。

- 作業概要
- 変更ファイル一覧
- 実施した検証
- 検証結果
- エラー詳細（ない場合はその旨）
- 未実施事項
- 残課題
- OWNER判断が必要な項目

詳細報告書は内部環境情報を含む可能性があるため、GitHubへPushしない。

指示書は `workspace/instructions/<AI名>/`、報告書は `workspace/reports/<AI名>/` に保存し、対応関係を追跡できる名前にする。AIごとに専用ディレクトリを使用する。

指示書・報告書を `/tmp` や任意の作業ディレクトリへ保存しない。`workspace/` はGit管理対象外とし、原則として指示書・報告書以外を保存しない。正式な設計書・API契約・テストコードはGit管理対象とする。

## 8. Git・本番操作

- 明示的な許可なしにcommit・pushしない。merge・tag作成も指示範囲に従う。
- force pushと既存履歴の書き換えは禁止する。
- 本番VPSへの変更・デプロイ・再起動は禁止をデフォルトとする。
- 破壊的操作は明示的な承認を必要とする。
- Git管理対象外のファイルを誤って追加しない。
- セキュリティ上の問題を発見した場合は隠さず報告する。

## 9. GitHub公開検証サマリー

公開可能な検証サマリーは `reviews/` に保存する。[管理目的と標準形式](../../reviews/README.md)に従い、以下を含める。

- 作業ID・作業名
- 実装または検証担当（自己検証か独立検証かを明示）
- 対象コミット
- 変更概要
- テスト結果
- 検証判定
- 未解決事項
- OWNER承認状態

詳細報告書と公開サマリーには同じ作業IDを付け、対応関係を追跡可能にする。公開サマリーのパスを詳細報告書に記録する。

判定はPASS、PASS WITH FINDINGS、FAIL、BLOCKED、NOT RUNを用い、第6節の基準に従う。実施していない検証をPASSと記載しない。

詳細報告書をそのままコピーせず、必要な情報だけを抽出する。秘密情報、内部IPアドレス、認証情報、個人情報、機密性の高い脆弱性情報を含めない。機密性の高い問題は公開サマリーに詳細を記載せず、非公開報告書でOWNERへ通知する。

`.gitignore` だけで秘密情報の流出を完全に防げるとは判断しない。共有前に公開対象の差分・新規ファイルとGit履歴を含めた秘密情報チェックを行う。

## 10. GitHubレビュー連携

共有先は `https://github.com/brokendish/HereRisk` とする。

OWNERが許可した範囲をcommit・pushし、GitHub上のProject Charter、アーキテクチャ設計書、API契約、ソースコード、テストコード、公開検証サマリー、コミット差分をChatGPTの成果物レビューに供する。

AIは検証対象のコミットSHAを報告し、可能な限りレビュー結果と対応付ける。未コミットの変更を検証した場合、対象コミットは「未コミット」と記載する。現在のHEADを未コミット変更の検証対象SHAとして扱わない。コミット後は実際の検証対象SHAを共有し、検証した内容との一致を確認する。追加変更があれば影響範囲を再検証する。

共有許可を得る前にcommit・pushしない。ChatGPTの成果物レビュー後、OWNERが最終承認し、次工程へ進む。本番VPSの変更・再起動・デプロイは別途OWNER承認を必須とする。

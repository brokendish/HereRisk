## 1. プロジェクトの目的

HereRiskは、利用者の現在地に関する地理情報と災害ハザード情報を取得し、その地点に存在する災害リスクを分かりやすく提示するWebサービスである。

利用者が地図上から危険情報を探すのではなく、現在地を起点として災害情報を自動的に取得する。

サービスの役割は、利用者の防災判断を支援することであり、安全を保証したり避難の可否を決定することではない。

**サービスは当初から全国対応を前提に設計する。** 初期の開発・実データ検証には東京都のデータを使用し、全国データの一括ダウンロード・整備は後続工程とする。

## 2. サービスコンセプト

**「今いる場所には、どのような災害リスクがあるのか？」**

この疑問に対して、位置情報を起点に、簡潔かつ根拠のある情報を提供する。

基本方針：

- 現在地を情報取得の起点とする。
- 数値だけでなく、その数値や区域情報の意味を伝える。
- 災害種別ごとに独立した判定を行う。
- 情報が取得できない場合は、その状態を明示する。
- 地図は現在地周辺を確認するための補助情報とする。
- スマートフォンでの利用を優先する。

## 3. 対象利用者

- 自宅や勤務先周辺のハザード情報を確認したい人
- 旅行先や外出先の土地勘がない人
- 自分の現在地の災害情報を手軽に知りたい人
- 災害への備えとして地域のリスクを確認したい人

専門知識を必要とせず、一般利用者が理解できる表現を採用する。

## 4. 開発基本原則

### P1. UNIX哲学

一つのモジュールは一つの責務を持つ。

各モジュールは可能な限り単独で実行・テストできる構造とする。

### P2. 疎結合

各モジュールの接続には明確なインターフェースとデータ契約を使用する。

他モジュールの内部実装やデータ保存方式に直接依存しない。

都道府県判定・データセット選択・ログ出力など、複数機能で共通する処理は `common` に集約し、重複実装を避ける。ただし、共通化は責務と契約が明確な処理に限定し、巨大な万能モジュールを作らない。

### P3. 小さなMVP

最小限の機能を完成させてから段階的に拡張する。

新しい機能を追加する際は、既存機能への影響と保守コストを評価する。

### P4. 独立検証

実装単位ごとにテスト可能な構造とする。

実装担当AIとは別のAIによる検証を実施し、最終判断はOWNERが行う。

### P5. 不明を安全と判定しない

データ未取得や取得失敗を、危険区域外であることと混同しない。

情報不足の場合は、判定不能または不明として利用者に伝える。

## 5. 提供する災害情報と全国対応方針

### 5.1 独立した機能分割

位置情報（緯度・経度）を入力とし、以下の5機能を独立した責務として扱う。

| 機能 | 提供内容 |
|---|---|
| 標高 | 現在地の推定標高 |
| 洪水 | 浸水想定区域該当有無・想定浸水深 |
| 津波 | 津波浸水想定区域該当有無・想定浸水深 |
| 高潮 | 高潮浸水想定区域該当有無・想定浸水深 |
| 土砂災害 | 警戒区域・特別警戒区域への該当 |

キキクル等のリアルタイム情報は将来の拡張候補とし、初期の5機能には含めない。

各情報は、データ取得元・データセット識別子・更新時刻またはデータ基準日・判定結果を可能な範囲で明示する。静的ハザード情報とリアルタイム情報は明確に区別する。

### 5.2 全国対応と地域データ選択

- システムの入出力契約とデータ管理体系は、当初から全国を対象に設計する。
- 初期のデータ取得・変換・検証・公開は東京都を対象に実施する。
- 全国のダウンロードとデータパイプライン実行は、初期MVPの必須条件としない。
- リクエストの緯度・経度から共通処理で都道府県を解決し、対象地点を評価できる適切なデータセットを選択する。
- データの収録範囲が都道府県単位とは限らないため、データセット選択では公開主体・対象範囲・災害種別等も扱えるようにする。
- 未整備の地域を危険区域外とみなしてはならない。

**目標は「東京専用処理を全国へ複製すること」ではなく、「汎用的な処理を東京で実証し、地域別データを追加して全国へ展開できること」である。**

## 7. リスク判定の基本方針

HereRiskは、災害情報の事実と利用者向け説明を分けて扱う。

洪水などのハザード判定では、少なくとも以下の状態を区別する。

- **該当：** 有効なデータに基づき対象区域内と判定できた
- **非該当：** 対象地点を評価できるデータがあり、その区域に該当しなかった
- **データ未整備：** 対象地点を判定するためのデータが存在しない、または対象外
- **取得失敗：** 通信・処理などの理由で情報を取得できなかった
- **判定不能：** データは存在するが、品質や整合性などの理由で判定できない

非該当は「安全」を意味しない。

すべての判定には、対象災害、根拠データ、評価時点に関する情報を紐付ける。

## 8. 技術アーキテクチャ方針

### 8.1 基本構成

初期構成は単純なWebアプリケーションを基本とする。

- **Frontend：** ブラウザからの現在地取得・情報表示
- **Backend API：** 入力検証・各機能の呼び出し・JSONレスポンス生成
- **`common`：** 都道府県判定、データセット選択、ログ出力などの共通処理
- **Hazard Modules：** 標高・洪水・津波・高潮・土砂災害の独立した取得・判定処理
- **Data Pipeline：** 地域別データの取得・正規化・検証・公開
- **Data Registry / Catalog：** データセットの識別、対象範囲、バージョン、公開状態の管理
- **Data Manager：** データ整備状況の確認とパイプライン実行・運用管理を行う管理画面
- **Data Sources：** 公開ハザードデータ・標高データ等

Backendは単一プロセス構成から開始できる設計とし、初期段階でのマイクロサービス化を必須としない。

### 8.2 共通処理 `common`

複数機能で必要となる共通処理は、重複させずに `common` として識別・管理する。

- **Location Resolver：** 緯度・経度から都道府県等の地域を解決する。
- **Dataset Selector：** 地域・災害種別・データの対象範囲等から利用対象のデータセットを選択する。
- **Logging：** 構造化ログ出力の共通方式を提供する。
- **共通契約：** エラー表現、データセット識別子、データ利用状態等の共通定義を提供する。

`common` は概念上のまとまりであり、内部を責務ごとに分離する。各災害モジュールが `common` の内部状態や他の災害モジュールの実装に依存しないようにする。

### 8.3 APIの原則

- 各災害種別は独立したAPIまたは独立して呼び出せるインターフェースを持つ。
- 利用者側は基本的に緯度・経度を指定する。都道府県やデータセットを利用者に選択させない。
- API内部で地域を判定し、対象地点に適切なデータを選択する。
- 応答はJSONとし、結果・状態・根拠データを区別する。
- 具体的なパス、フィールド名、型、ステータスコードはAPI契約定義工程で確定する。

### 8.4 汎用データパイプライン

データパイプラインは **取得（Download）→ 正規化（Normalize）→ 検証（Validate）→ 公開（Publish）** を基本段階とする。

東京のデータで動作を確認した共通処理を、別地域にも再利用できるようにする。元データの提供形式や公開単位の違いは、設定や入力アダプターで吸収する設計を目指す。地域固有の差異により追加対応が必要になることは許容する。

**検証を通過していないデータを公開側から参照させない。** 公開済みデータの識別子・バージョン・整備状態を確認可能とする。

### 8.5 データ管理画面

データの追加・更新・整合性確認が継続的に必要なため、OnHighGround2での経験を踏まえ、管理画面を当初からアーキテクチャの対象に含める。

管理対象は、地域・災害種別ごとの整備状況、取得・変換・検証・公開の状態、エラー、データ更新情報、公開バージョン等とする。操作機能は段階的に実装する。

管理画面および管理APIは一般利用者向け公開APIと分離し、認証・認可を設ける。MVP 0では管理画面の完成を必須としない。

## 9. OnHighGround2との関係

OnHighGround2は、HereRiskの重要な技術的知識源として扱う。

再利用の対象：

- 災害データに関する知識
- データソースの調査結果
- 取得処理や地理判定に関する設計知見
- テストで確認された仕様
- 運用・公開監査で得られた経験

**既存コードの直接コピーを前提としない。**

再利用する場合もHereRiskの責務・API契約に適合することを確認し、必要なテストを実施する。

## 11. MVP 0 完了条件

以下の条件をすべて満たした時点でMVP 0を完了とする。

- 緯度・経度を入力して標高を取得できる
- ブラウザの現在地から標高を表示できる
- 位置情報拒否・タイムアウトを適切に表示できる
- データ欠損・通信失敗を正常結果と区別できる
- 地域判定とデータセット選択を共通機能として分離する設計が文書化されている（MVP 0で不要な実装は強制しない）
- APIの入出力形式が文書化されている
- モジュール単体テストが成功する
- 契約テストが成功する
- Codexの検証結果が受入基準を満たす
- OWNERが動作と表示を確認する

## 12. 成功基準

HereRiskの初期成功は機能数では測定しない。

重視するのは以下の4点とする。

- シンプルな構造を維持できている
- 一つの機能を他へ大きく影響させず変更できる
- データ取得・判定の失敗を確実に検出できる
- 新しい災害情報を既存の契約を維持しながら追加できる
- 同一の処理を都道府県別に複製せず、地域データ追加による全国展開を目指せる
- データの整備状態と公開状態を管理し、不明を安全として扱わない

- **境界の包含は公式に未規定である。** 製品仕様書は「0m および各ランク境の値ランクが公表図と異なることがあるのは、『洪水浸水想定区域図作成マニュアル（第4版）』においては、境界値の『以上』『未満』が規定されていないためである」と明記している。指示書の表（「0m以上～0.5m未満」等）の下限「以上」は、原典では確定していない。
- コード5の「内容」欄が「津波基準水位を表現する」となっている（洪水の説明として不自然。原典の記載のまま記録する）。
- 重複の扱い（応用スキーマ文書）: 「**一つのデータ内に**複数のポリゴンがオーバーラップする場合は、浸水ランクコード…の値の大きい方を優先し…オーバーラップの無いデータとする」。異なるデータ（ファイル）の間の重複については定めがない。
- 統合（同）: 原典が複数河川を統合したデータの場合は、河川単位に分離できないためそのまま使用。同一管理者内の同一河川が複数ファイルに分かれている場合は統合。

### 2.4 注意事項［公式］（データページ）

- 支川の氾濫、前提となる降雨を超える規模の降雨、**高潮および内水による氾濫等は考慮していない**。指定されていない区域でも浸水が発生する場合や、実際の浸水深が想定より大きい場合がある。
- **東京都**: 独自の施策として、洪水予報河川・水位周知河川以外の河川からの外水氾濫や内水氾濫での浸水も表示した「浸水予想区域図」を作成・公表しており、区市町村はこれを基にハザードマップを作成している。そのため住民のハザードマップと浸水域が異なる場合がある。
- 河川は国管理と都道府県管理があり、**国管理河川は開発局・地方整備局単位でデータを整備**している。
- 階級は製品仕様書の値で区分しているため、一部公表図と着色が異なる場合がある。

## 5. 河川・カバー範囲の調査結果

1. **東京都のZIPは都管理河川だけである**［実測］。荒川・多摩川（国管理区間）・江戸川・中川（国管理区間）・綾瀬川（同）・浅川（同）・大栗川（同）などの国管理河川は、関東地方整備局の配布単位（507.39MB）にある［公式］。東京都の主要な洪水リスク（荒川・江戸川・多摩川）を扱うには、**国管理河川の補完が必要**である。
2. 都管理河川の一部（芝川・新芝川）は埼玉県のファイル、鶴見川の国管理区間は神奈川県のファイルにある［公式］。「東京都のZIPだけで東京都内を網羅できる」とは言えない。
3. 1ファイルに複数の河川が統合されており、属性の河川名は代表の1河川だけである［公式・実測］。応答の「河川名」は、厳密には「データ（成果品）の代表河川名」である。
4. 配布単位の間（都管理ファイル同士）で重複がある［実測: 18/15,958点］。仕様書は同一データ内の重複だけを解消している［公式］。国管理と都管理の間の重複（例: 隅田川と荒川）は、関東地整のデータを取得していないため**未確認**。
5. **「区域外」と「データ未整備」を区別できる根拠はない**［公式・実測］。A31aは浸水想定区域のポリゴンだけを持ち、「評価した範囲（河川の流域・対象範囲）」を表すデータを含まない。また、データページは「指定されていない区域でも浸水が発生する場合がある」と明記している。**ポリゴンに該当しないことは、浸水リスク0や区域外を意味しない。**
6. 旧中川などのファイルの備考に「洪水による浸水なし(内水のみ)」とある［公式］。このファイルのポリゴン（3,257件）が何を表すかは、資料からは判断できない（未確認）。

## 6. 空間検索方式の比較［提案］

| 観点 | 1. SQLite RTree + Point-in-Polygon | 2. GeoJSONファイルの直接検索 | 3. 簡易格子索引 + PIP（メモリ上） |
|---|---|---|---|
| 前処理 | 必要（Normalize段でポリゴンを読み、外接矩形をRTreeへ、座標をBLOB等へ） | 不要 | 起動時に毎回構築（数秒〜） |
| VPSのメモリ | 小さい（必要なポリゴンだけ読む。RTree約26万行） | 大きい: 1ファイルの全読込みでRSS 190〜344MB［実測］。全15ファイルを常駐させると、現在のAPIの上限256MiBを超える見込み | 全座標の常駐が必要（約600万頂点）。2と同程度以上 |
| 1地点の計算量 | O(log n + 候補数×頂点数) | 全ファイル走査ならO(n)。実測で約40ms（1地点・全ファイル、Python） | O(候補数×頂点数) |
| MultiPolygon・穴 | 対応可（PIPで穴を除外） | 同左 | 同左 |
| 境界上の点 | 規則を決める必要あり（全方式共通） | 同左 | 同左 |
| データ更新・差替え | 新しいDBファイルを作り、Registryで原子的に切替え（既存のPublish/Registryの方式に合う） | ファイル差替えだけ | 再起動で再構築 |
| 既存パイプラインとの整合 | 高い（Download → Normalize → Validate → Publish → Registry → API の公開実体として扱える。標準ライブラリの `sqlite3` で済み、依存を増やさない） | 低い（原典をそのまま公開実体にする） | 中 |

**推奨（未決定）**: 1. SQLite RTree + Point-in-Polygon。理由は、メモリの制約（VPSのSwap使用が多い）、既存の不変な公開実体とRegistryの方式との整合、標準ライブラリだけで実装できること。境界上の点の規則は、全方式で別途決める必要がある（第7章）。本調査では、検索エンジンやベンチマークの本格的な実装はしていない。

## 7. Flood API v0.1 の契約案［提案・未決定］

Request（指示書の基本案）:

```json
{"lat": 35.681236, "lon": 139.767125, "scenario": "maximum"}
```

判定区分の案:

| status | 条件 | A31aでの判定可否 |
|---|---|---|
| `inundation_zone` | 地点が1つ以上の浸水想定区域ポリゴンの内部にある | 可能 |
| `outside_inundation_zone` | 地点が、評価済みの範囲の中で、区域ポリゴンの外にある | **A31aだけでは判定できない**（評価範囲のデータがない。第5章の5）。v0.1では使わないことを提案する |
| `not_covered` | 地点が、HereRiskが公開しているデータの対象地域（例: 東京都）の外にある | 対象地域の境界データ（行政区域）を別に用意すれば可能 |
| `unknown` | 対象地域の中で、どのポリゴンにも該当しない（区域外か、データ未整備か、考慮外の要因かを区別できない）。またはデータの欠損・不整合 | 可能（「浸水しない」とは表示しない） |

結果の構造の案:

```json
{
  "hazard": "flood",
  "scenario": "maximum",
  "status": "inundation_zone",
  "result": {
    "representative_rank": {"code": 2, "label": "0.5～3.0m未満", "depth_min_m": 0.5, "depth_max_m": 3.0},
    "zones": [
      {"rank": {"code": 2, "label": "0.5～3.0m未満", "depth_min_m": 0.5, "depth_max_m": 3.0},
       "river_code": "8303040011", "river_name_in_source": "隅田川",
       "river_manager_code": "13", "river_manager": "東京都",
       "source_unit": "A31a-20-25_13_8303040011_20"}
    ],
    "notes": ["rank_is_not_measured_depth", "boundary_inclusion_unspecified_in_source",
              "storm_surge_and_inland_flooding_not_considered"]
  },
  "dataset": {"id": "...", "publication_version": "...",
              "attribution": {"text": "「国土数値情報（洪水浸水想定区域データ）」（国土交通省）（URL）を加工して作成",
                              "license": "CC BY 4.0 互換（国土数値情報ダウンロードサイトコンテンツ利用規約）", "url": "..."}}
}
```

- 浸水深ランクは、実測の浸水深や正確な推定値ではない。`label` に原典の定義の文言を保持する。`depth_min_m`・`depth_max_m` は原典の区分の数値だけを表し、**境界の包含は原典で未規定**（2.3節）であることを `notes` 等で明示する。ランク6は `depth_max_m: null`。
- 複数のポリゴンに該当する地点では、`zones` に全件を残す（実測で、ランクが異なる重複が5点あった）。`representative_rank` は最大値方式を第一候補とする（仕様書の「同一データ内の重複は値の大きい方を優先」と整合する）。ただし、国管理河川との重複状況を確認するまで正式には確定しない。
- `river_name_in_source` は、統合ファイルの代表河川名である（Feature単位の河川を表さない）。
- 既存のElevation APIの共通部分（`hazard`・`status`・`result`・`dataset`・`error`・`evaluated_at`、Bearer認証、ログに座標を残さない）を参考にする。既存APIの改修はしない。
- 座標系: 入力はWGS84、データはJGD2011。位置正確度（標準偏差50m）に比べて差は小さいと考えられるが、同一とは扱わず、扱いを契約に明記することを提案する。

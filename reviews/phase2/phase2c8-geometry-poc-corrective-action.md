## 2. C7-01・C7-02の原因と修正方式

### 2.1 原因

**C7-01**: Phase 2-C.6の判定器（以下「旧判定器」）は、次の手順で丸めの影響を見ていた。

- 丸め前後それぞれについて、「有効か無効か」と「異常の分類の集合」だけを返す。
- 丸め前後でその集合を比べる。

接触点は、判定器の内部の連結性判定に使うだけで、外に返していなかった。そのため次の変化を見逃す。

- 前後とも有効のまま、新しく接触が生じた場合（C7-01の反例）
- 既に無効な形状に、同じ分類の異常が1つ増えた場合

**C7-02**: 旧判定器は、環を頂点、「接している環の組」を辺とするグラフを作り、閉路があれば内部非連結とした。

- 3つの環が同じ1点で接すると、環のグラフには3角形の閉路ができる。
- しかし、幾何学的には内部を分断していない。
- 原因は、「どの点で接しているか」を判定に使っていなかったことである。

### 2.2 修正方式（責務の分離）

判定器を、指示書第3章のA・Bに分けて作り直した（`geom.py`）。どちらも整数で厳密に計算し、浮動小数は使わない。

**A. 幾何形状の妥当性の判定**（`analyze`）。結果は valid / invalid / inconclusive と、理由・位置の一覧。

| 検査 | 方式 | 無効の理由のコード |
|---|---|---|
| 環の閉包・点数・面積0 | 連続する重複頂点をまとめた写しで判定する（原典・丸め後の配列は変更しない） | `ring_not_closed`, `degenerate_ring` |
| 同じ環の中の辺の関係 | 全ての辺の対を整数の向き判定で分類する（交差・同一直線上の重なり・接触） | `ring_self_cross`, `ring_self_overlap`, `ring_spike_or_self_overlap`, `ring_self_touch` |
| 異なる環の辺の関係 | 同上 | `rings_cross`, `rings_overlap` |
| 接点での横断 | 接点から出る両方の環の2本ずつの方向を、厳密な角度順に並べる。交互に並べば横断と判定する | `rings_cross_at_point` |
| 内部の連結性 | 環と接点を節点とする二部グラフ（環が接点を通れば枝）に閉路があれば非連結と判定する | `interior_disconnected` |
| 穴の位置 | 境界上にない試験点（頂点、または座標を2倍した辺の中点）の厳密な点の内外判定 | `hole_outside_shell`, `nested_holes` |

二部グラフにすると、同じ1点で何個の環が接しても、その点を中心とする星形になり、閉路はできない（C7-02の形は有効）。一方、2つの環が異なる2点で接すれば「環→点→環→点→環」の閉路ができ、非連結と判定する。

**B. 丸め前後の関係の変化の検出**（`diff`）。丸め前後の同じ多角形について、次をすべて照合する。差があれば、種類・位置・前後の状態・根拠を記録する（第5章）。

- 正常な隣接関係を除く、全ての辺の対の関係
- 環の事実（閉包・縮退・向き・連続する重複頂点の数）
- 穴の包含関係
- 環の組ごとの接点の数
- Aの判定

辺は、原典の頂点番号の組（環番号、始点番号、終点番号）で識別する。そのため丸め前後で同じ辺どうしを対応させられる（RC-1で構造が保たれることが前提）。

**Codexの反例を特別扱いしていない。** 判定器には反例の座標・形状に依存する分岐はない。反例は回帰テストの入力として使うだけである（第6章）。

### 2.3 そのほかの修正（監査の第3章の指摘）

| 指摘 | 修正 |
|---|---|
| 数値と引用符付きの数値文字列を区別できない | JSONの数値を専用の文字列型（`NumTok`）で受け取る。座標が文字列なら `coordinate_not_number` として拒否する |

## 3. RC-6の検査対象（明確化）

方針案のRC-6（丸めによる妥当性・接触等の変化）について、本PoCの判定器Bが検査する対象と、検査しない対象を次のように定める［提案］。

| 区分 | 検査する対象 | 識別・比較の方法 |
|---|---|---|
| B-1 辺の対の関係 | 同じ多角形の全ての辺の対（同じ環の隣接しない辺、隣接する辺の異常、外周と穴、穴と穴）の関係<br>・種類: 交差 / 同一直線上の重なり / 接触<br>・どの端点が相手のどこ（端点か内部か）にあるか | (環, 始点番号, 終点番号) の組。前後の集合の差 |
| B-2 環の事実 | 閉包、縮退、向き（符号付き面積の符号）、連続する重複頂点の数、残る頂点の数 | 環番号ごとの比較 |
| B-3 包含関係 | 穴が外周の外にあるか、穴が別の穴の中にあるか | 事実の集合の差 |
| B-4 接触グラフ | 環の組ごとの異なる接点の数 | 環の組ごとの比較 |
| B-5 妥当性 | Aの判定と分類 | 前後の比較 |

- **RC-6の不成立**: B-1〜B-5のいずれかに差があるもの。
  - 現時点の方針案のRC-6では、取込みをBLOCKEDにする条件として扱う。
  - 変化の種類ごとに許容するかどうかは、OWNERの判断事項とする（第13章）。
  - B-1が検出する新しい接触・接触の消失・接触の種類の変化は、前後とも有効であっても不成立に数える。
- **検査しない対象**: 次は本PoCのRC-6の範囲外である（第11章）。
  - 別のFeatureとの関係（隣接する区域の重なり・隙間）
  - MultiPolygonの部分どうしの関係（部分が2つ以上のFeatureは inconclusive とする。今回のデータでは該当なし）
  - 境界の近傍の地点で内外判定の結果が変わること（境界の移動量は、RC-7の変位の上限で扱う）

### 4.2 C7-04 形式間照合の仕様案（契約案・未承認）

**5つの表現**（混同しない）

| 記号 | 表現 |
|---|---|
| R1 | GeoJSONの原典の十進トークン（ソースの文字列が表す正確な十進の値） |
| R2 | ShapefileのIEEE 754 binary64の値 |
| R3 | R2の最短の十進表記（同じbinary64に戻る最短の文字列。Pythonの `repr`） |
| R4 | R2の厳密な十進展開（`Decimal(float)`） |
| R5 | 小数8桁に丸めた検索用の座標（`ROUND_HALF_UP`） |

**3つの照合**

照合の目的が異なるため、形式間の同一性（V1）と、検索用の丸めの一致（V2）は別の照合とする。

| 照合 | 目的 | 一致の条件 | 許容差 | 比較できない場合 |

### 4.3 C7-03 資源制限

**方式**: 処理の全体（インタプリタの起動、ZIPの読込み、JSONの解析、全ての判定、集計、結果の書込み、Shapefileの照合）を子プロセスで実行する。外部の監督プロセスが、次のように監視・制限する。子プロセスの中の監視（旧 `guard()`）は使っていない。

| 資源 | 強制の方式 | 保証 |
|---|---|---|
| 実時間 30分 | 監督プロセスが0.1秒ごとに確認し、超過したらSIGKILL | 監督プロセスが動作している限り、超過から約0.1秒以内に停止する |
| CPU時間 30分 | 子プロセスに `RLIMIT_CPU` を設定する（カーネルが強制） | カーネルが停止させる（SIGXCPU） |
| メモリ 2GB | 監督プロセスが0.1秒ごとに子の常駐サイズ（libproc）を確認し、超過したらSIGKILL。終了後、カーネルが記録した最大RSS（`wait4` の `ru_maxrss`）を上限と照合する | **防止は保証しない**（1回の監視間隔の間に確保された分は超過しうる）。**超過の検出は保証する**（カーネルの記録による） |

macOSのメモリのrlimitの確認結果:

- `RLIMIT_AS` / `RLIMIT_DATA` / `RLIMIT_RSS` は、設定自体が失敗した（"current limit exceeds maximum limit"）。
- 設定しないまま1GBを確保しても、止まらなかった。

したがって、カーネルによるメモリの強制はできない。

**超過試験**（合成の子プロセス。データは使わない）

| 試験 | 条件 | 結果 | 状態 |
|---|---|---|---|
| メモリが徐々に増える | 上限300MB、100MBずつ確保 | 0.59秒で強制終了。最大RSS 329.6MB（**上限を約30MB超過してから停止**） | `KILLED_MEMORY` |
| 実時間 | 上限3秒、sleepを続ける | 3.06秒で強制終了 | `KILLED_WALL_TIME` |
| CPU時間 | `RLIMIT_CPU` 2秒、空ループ | 2.05秒でカーネルが停止 | `KILLED_CPU_RLIMIT` |
| 監視の間の一時的な確保 | 上限300MB、監視間隔2秒、800MBを瞬間的に確保して解放 | 監視では検知できず（観測は0.6MB）。事後に、カーネルの記録852MBで超過を検出した | `LIMIT_EXCEEDED_POSTHOC_MEMORY` |
| 正常 | — | 完了 | `COMPLETED_WITHIN_LIMITS` |

**扱い**:

- 状態が `COMPLETED_WITHIN_LIMITS` の実行だけを、結果として使える（`result_usable`）とする。
- 強制終了・事後の超過検出・子のエラーは、途中結果があってもPASSとして扱わない。
- 本工程の実データの実行は、全件 `COMPLETED_WITHIN_LIMITS` だった。最大RSSは、A49のShapefile照合の約0.99GBだった（第10章）。

**残る制約**:

- メモリは、上限ちょうどでの停止を保証できない。
- 監督プロセス自体が異常終了した場合に子を止める仕組み（プロセスグループの監視等）はない。
- 常駐サイズには、macOSの圧縮メモリの分は含まれない。

指示書は「強制停止を保証できない場合は、その制限を明記して実行を保留する」としている。本工程では、次の理由で実行した。

- 超過時の停止そのものは監督プロセスが行う。
- 超過の事後検出はカーネルの記録で保証される。
- 実際の最大使用量は上限の半分以下だった。

この解釈が不十分と判断される場合は、本工程の実データの結果を保留として扱う（OWNER判断事項）。

## 11. 残る未検証条件

1. **判定器A・Bの独立監査**。整数で厳密に計算する独立した2つ目の実装はない（GEOSは倍精度の参考）。
2. **MultiPolygonの部分どうしの関係**。部分が2つ以上のFeatureは inconclusive にする設計で、今回のデータでは該当がなく、動作は試験していない。
3. **Feature間の関係**。隣接する区域・行政区域の重なりや隙間の、丸めによる変化は検査していない（RC-6の範囲外。統合の工程で扱うかはOWNERの判断事項）。
4. **境界の近傍の地点の内外判定**。境界は最大5×10⁻⁹度動くため、その範囲の地点の判定は変わりうる。これはRC-7の変位の上限として扱い、位相の検査の対象にしていない。
5. **計算量**。辺の対の掃引は、最悪の場合に二次時間になる。全国規模の入力・本番VPSでは測っていない。
6. **メモリ上限の強制**（第4.3節）。カーネルの上限を設定できず、1回の監視間隔分の超過と、圧縮メモリの分は防げない。
7. **許容差T**。Tより小さい形式間の差は検出できない（変異試験M3）。Tの値（PoCでは1×10⁻¹²度）は未承認である。
8. **A49のDBFの文字コード**。`.cpg` がなく、cp932は照合の結果からの推定である。
9. **GMLとの照合**。本工程では再実行していない（Phase 2-C.4・2-C.5の結果のまま）。
10. **Phase 2-C.6の実行の証跡**（第4.1節）。NOT VERIFIEDのままである。
11. **入力検証の範囲**。GeoJSONの構造の全項目（型の組合せ、BOM、`bbox` 等）の検証は、製品のNormalizeの範囲として未実装である。
12. SQLite・RTreeの生成、地点検索・APIの性能は、本工程の範囲外である（作成していない）。

## 3. `result_usable` の新しい判定仕様

監督プロセスは、実行ごとに次の3つの状態を**別々に**記録する（`runs*/<run_id>/manifest.json`）。

| 状態 | 意味 | 成立の条件 |
|---|---|---|
| `resource_status.ok` | 資源の条件を満たし、監視が完全だった | 次の所見が1つもないこと<br>`KILLED_WALL_TIME` / `KILLED_MEMORY` / `KILLED_CPU_RLIMIT` / `CPU_LIMIT_EXCEEDED_POSTHOC` / `MEMORY_LIMIT_EXCEEDED_POSTHOC` / `MEMORY_LIMIT_EXCEEDED_POLLED` / `WALL_LIMIT_EXCEEDED_POSTHOC` / `MONITORING_FAILED` / `DESCENDANTS_LEFT_RUNNING` / `PAYLOAD_REPORT_MISSING` |
| `integrity_status.ok` | 成果物がこの実行のもので、完全で、入力・設定・コードと対応する | I1〜I11がすべて成立すること（下表） |
| `result_usable` | 成果物をこの実行の出力として読んでよい | 上の2つがともに成立すること（I9で、payloadが完了を宣言していることも含む） |

`result_usable` は、成果物を読んでよいという意味に限られる。**いずれかの検査のPASSを意味しない。** payloadが記録した評価不能は、評価不能のまま残る（`payload_declared` に併記する）。

**成果物の完全性の検査（I1〜I11）**

| ID | 検査 | 内容 |
|---|---|---|
| I1 | 正常終了 | payload（launcherが回収した対象のプロセス）の終了コードが0 |
| I2 | 必須成果物の存在 | specの `required_artifacts` がすべてある |
| I3 | 形式 | JSONとして読める。証跡のJSONLは `evidence.verify` が合格する（ヘッダ、連番、件数、種類ごとの件数、本文のSHA-256、宣言した一覧の要素数） |
| I4 | run_idの一致 | 要約JSONの `run_id`、および証跡の**全行**の `run_id` が、この実行のrun_idと一致する |
| I5 | 作成時刻 | 成果物の更新時刻が、実行の開始から終了の間にある |
| I6 / I6b | 入力の同一性 | 入力ZIPのSHA-256が実行の前後で同じである。さらに、payloadが実際に読んだバイト列のSHA-256がそれと一致する |
| I7 / I7b | 設定 | 監督プロセスが作った設定のスナップショットが、実行の後も変わっていない。payloadが報告する設定のSHA-256が、スナップショットと一致する |
| I8 / I8b | コード | 監督プロセスが実行の前後でハッシュしたコードが変わっていない。payloadが報告する自分のコードの全ファイルが、監督プロセスのハッシュと一致する（ハッシュしていないコードを実行していない） |
| I9 | 完了 | payloadが `completion: "complete"` を宣言している（`partial`・`input_rejected`・`input_hash_mismatch` は利用不可） |
| I10 | 要約と証跡の対応 | 要約が参照する証跡の件数・種類ごとの件数・本文のSHA-256が、証跡のフッタと一致する |
| I11 | 余分な成果物がない | 出力ディレクトリに、宣言していないファイルがない |

**古い実行の成果物の誤用を防ぐ仕組み**

- 実行ごとに、新しい空の出力ディレクトリ `runs*/<run_id>/out/` を作る。既にあれば作成に失敗する。
- その上で、I4（run_id）・I5（時刻）・I10（対応）で照合する。

**監視の変更点**

- payloadは、新しいプロセスグループの先頭（launcher）の下で実行する。メモリはグループ全体の合計で監視する。
- 動作中のプロセスの値を取得できなければ監視の失敗とし、0として扱わない。ゾンビは `ps` で区別する（終了済みで、メモリは解放されている）。
- CPU時間は、soft・hardの設定に加えて、実測のCPU時間（user + sys）を設定値と照合する。

## 5. 完全な証跡と表示用要約の分離方式

**A. 完全な機械可読証跡**（`out/evidence.jsonl`。形式 `hererisk-poc-evidence-jsonl/1`）

| 行 | 内容 |
|---|---|
| 1行目 ヘッダ | `run_id`、形式、検査条件、コードの全ファイルのSHA-256、入力ZIPとメンバーのSHA-256、設定のSHA-256、位置の座標の単位 |
| 項目の行 | 種類ごとの行。`run_id`・連番・種類を持つ。一覧は**全要素**を書き、要素数 `n_<名前>` を添える<br>種類: `A_invalid` / `A_inconclusive`（無効・評価不能の全理由と位置）、`RC6_change`（全変化）、`RC1`〜`RC5`、`legacy_vs_new`、`new_vs_geos`、`decimal_mismatch`、`input_rejected_*` |
| 最終行 フッタ | 項目の数、種類ごとの件数、本文（全項目の行）のSHA-256 |

位置は次のとおり記録する。

- Feature: 出現順と識別属性
- Polygon: 番号
- ring・edge: （環番号、始点の頂点番号、終点の頂点番号）
- vertex: RC-3は頂点番号の一覧、理由は接点の座標の整数

- 書込みは1項目ずつのストリーミングである。メモリに蓄積するのは件数とハッシュだけである。
- 入力のJSON全体の読込みは、C.8と同じく一括のままである（第8章）。

**B. 表示用の要約**（`out/summary.json`）

- 件数、種類ごとに上限付きの例（`display_limit`）、完全な証跡への参照（パス、項目の数、種類ごとの件数、本文のSHA-256）を持つ。

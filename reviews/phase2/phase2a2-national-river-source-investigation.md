| B. HTTPのRangeリクエストで、ZIPの中央ディレクトリと必要なメンバーだけを取得 | サーバーは `accept-ranges: bytes` を返す。末尾の中央ディレクトリ（推定で数十〜数百KB）を読み、必要なメンバーの範囲だけを取得し、メンバーのCRC32で検証 | 通信量を大幅に減らせる見込み | ZIP全体のSHA-256は検証できない。公式に案内された取得方法ではない。サーバー側の扱いが変わると再現できない。**これもZIPの一部の取得であり、OWNER承認が必要** |
| C. ZIPの中央ディレクトリだけを取得して、内部のファイル一覧を確認 | Bの前段（一覧の確認だけ） | 取得の判断材料（メンバー名・サイズ）を得られる | 同上 |

推奨［提案］: **A**（公式の取得方法と完全なハッシュを優先）。通信量を抑えたい場合は、先にCで内部構成を確認する。いずれもOWNERの承認後に行う。

## 8. Dataset Registry のメタデータ案［提案］

### 8.1 既存設計との関係

- 公開Registryは、`validation.status = passed` のデータセットだけを登録する（Dataset Registry設計 §3.8）。取得中・未検証のデータは公開Registryに入れない。
- 「取得済み・検証済み・公開済み」は、Source Definitionに状態として書かず、Acquisition Record・検証証跡・公開Registryで別々に確認する（データソース定義設計 §4）。
- 標高APIの実装（Phase 1-D〜1-H）は、この3層（Source Definition → 記録 → 公開Registry）に沿っている。

そこで、要求された項目を、次の3層に分けて管理することを提案する（**既存の実装・Schemaは変更しない**）。

### 8.2 層1: Source Definition（`api/flood/conf/sources.json` 相当。静的な定義）

```json
{
  "sources": {
    "ksj-a31a-2025-83-10-maximum": {
      "provider": {"id": "mlit-ksj", "name": "国土交通省 国土数値情報"},
      "dataset_identifier": "A31a",
      "reference_year": "2025",
      "distribution_unit": {"manager_code": "83", "manager": "関東地方整備局", "river_class": "10"},
      "source_file": "A31a-25_83_10_GEOJSON.zip",
      "source_url": "https://nlftp.mlit.go.jp/ksj/gml/data/A31a/A31a-25/A31a-25_83_10_GEOJSON.zip",
      "official_page_url": "https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-A31a-2025.html",
      "scenario": "maximum",
      "members": ["A31a-20-25_83_8303040001_10", "A31a-20-25_83_8303030284_10"],
      "coverage_evidence": [
        {"member": "A31a-20-25_83_8303040001_10", "level": "listed_in_official_datalist",
         "basis": "A31_R7_datalist.xlsx 想定最大規模: 荒川, 荒川下流河川事務所, mesh 5339"}
      ],
      "usage": {"terms_url": "https://nlftp.mlit.go.jp/ksj/other/agreement_01.html",
                "license_label": "CC BY 4.0 互換（国土数値情報ダウンロードサイトコンテンツ利用規約）",
                "attribution_text": null, "review_ref": null},
      "approval_ref": null
    }
  }
}
```

- `coverage_evidence.level` は、`listed_in_official_datalist`（一覧に掲載）→ `spatially_verified`（取得後、ポリゴンが対象地域内にあることを確認）の順に強くなる。**一覧の掲載やメッシュの一致だけでは、対象地域のCoverageとして扱わない。**
- `usage.review_ref`（利用条件の確認記録）と `approval_ref`（取得・公開の承認）は、OWNERの判断までnull。

### 8.3 層2: 記録（状態は記録の有無と内容から導く）

| 状態 | 記録 | 内容 |
|---|---|---|
| download status | Acquisition Record | 取得日時、URL、HTTPヘッダー（Last-Modified・ETag・Content-Length）、ZIPのSHA-256・サイズ、展開したメンバー名・サイズ・SHA-256 |
| license / usage review | 利用条件の確認記録（`usage.review_ref` が指す、リポジトリ外の記録） | 確認日、確認した条件、未解決事項の扱い、確認者 |
| validation status | Validate記録 | profile、属性・ジオメトリの検査結果、Coverageの空間的な確認の結果 |
| publication status | 公開Registry | 検証に合格し、Publishした版だけ |

**取得したこと・利用条件を確認したこと・検証に合格したこと・APIで公開したことは、それぞれ別の記録で表し、どれか1つから他を推定しない。**

### 8.4 層3: 公開Registry（既存の項目への対応）

| 要求項目 | 既存のRegistry項目 |
|---|---|
| source provider | `source.provider` |
| dataset identifier | `source.original_version`（`A31a 2025`）または `acquisition.parameters`（未決定） |
| distribution unit / source file / source URL | `source.filename`（ZIP名）、`acquisition.url`、`acquisition.parameters.member`（成果品名） |
| manager / scenario / reference year | `acquisition.parameters`（`manager_code`・`scenario`・`reference_year`） |
| geographic coverage | `coverage`（洪水の形式は未決定。標高のP2はXYZタイル用で、ポリゴンには使えない） |
| license / attribution | `attribution.text`・`license`・`url` |
| validation / publication | `validation`・`publication`（既存どおり） |

既存のRegistryは「1データセット=1つの公開実体」である。複数の成果品（GeoJSON）を1つのSQLite公開実体にまとめる場合、`source.filename` の複数ファイル表現が必要になる（Dataset Registry設計 §3.5で「複数ファイル表現はUNDECIDED」）。これはPhase 2-A.3以降の契約で決める。

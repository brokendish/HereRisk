## 2. 指摘ごとの対応

### B7-01 — HIGH：公開準備状態の確定が循環依存している

**指摘の概要**

Integration Recordに記録する `ready` は後続のIntegrated Validateの合格を前提とする。一方、Integrated ValidateはIntegration Recordのハッシュを対象として保持し、IV-22でその公開準備状態を検証する。暫定値で確定すると、検証後に `ready` へ変えた時点でハッシュが変わる。変えなければ、合格後も公開可能な状態へ移れない。また、`ready` と `blocked_other` の条件が同時に成立しうるのに、複数の阻害理由の扱いが定められていない。

**修正箇所**: I §2（工程の表・確定順序）、§6.6、§7.1、§7.2（来歴の連鎖）、§7.3（全面改訂）、§8.1 IV-22、§8.2、§9.2、§11.1・§11.2、§12 I-01・I-27・I-29〜I-31、§13 OI-20・OI-28

**具体的な修正内容**

- 確定順序を一方向にした: Integration Record → Integrated Validate Record → **Publication Readiness Record（新設の別Record）** → Publish記録。各Recordは前段をハッシュで参照するだけで、前段を変更しない。
- Integration Recordは生成の事実（入力・出力のハッシュ・件数）だけを記録する。`publication_readiness` 項目を廃止した。
- IV-22（公開準備状態の検証）をIntegrated Validateから外した。Integrated Validate Recordからも `publication_readiness` 項目を削除した。
- Publication Readiness Recordの内容を定義した。対象のDB・Integration Record・Integrated Validate Recordのハッシュ、unknownポリシーと承認記録、利用条件、認可、照合した時刻（`evaluated_at`）、`readiness`、`blockers[]` を持つ。
- `ready` は「全必須条件が成立し、かつ `blockers` が空」と定義した。阻害理由は配列ですべて記録し、優先順位で1つに絞らない。利用条件の未解決、unknownポリシーの未承認、認可の期限切れのいずれかがあれば `ready` にしない。
- Publishは、`ready` のReadiness Record 1つを `record_sha256` で指定して受け取る。そのうえで、Publish時点の時刻と失効一覧で、承認・利用条件・認可を再確認する（I §9.2）。
- 既存のData Publish契約との接続点を明記した（I §7.3末尾）。`candidate_id` が指す検証済み候補を、Readiness Recordとそれが固定した成果物に対応させる案である。既存の公開条件（`license`・`attribution_url`・`attribution_text`・`eligibility_status`）は、そのまま要求する。既存契約は変更していない。

**反例に対する受入条件**

| 反例 | 受入条件 | テスト |
|---|---|---|
| 検証前に `ready` を確定する | Readiness Recordは、PASSのIntegrated Validate Recordがなければ `ready` にならない。Integration Recordには `ready` を書く項目がない | I-29 |
| 検証後に `ready` へ書き換えてハッシュが変わる | 検証の前後とReadinessの作成後で、Integration Record・Integrated Validate Recordのバイト列と `record_sha256` が不変 | I-30 |
| unknownポリシーは承認済みだが、利用条件が未解決・承認が失効 | `blocked`。阻害理由を両方とも記録する。Publish直前の再確認でも拒否する | I-31・I-38 |
| Publishが信頼するRecordが一意に定まらない | Publishは `record_sha256` で指定した1つのReadiness Recordだけを受け取り、それが固定するDB・各Recordのハッシュとの一致を確認する | I §9.2、I-16 |

**文書上の解決状況**: RESOLVED（文書）。循環依存は契約から除いた。

**アルゴリズム・実装上の未検証事項**

- Readiness Recordの正確なSchema・阻害理由コードの最終的な一覧。
- Publish直前の再確認を、既存のPublish処理のどこで行うか。既存のElevation Publish実装は `api_id="elevation"` と既存のValidate Recordに依存しており、Readiness Recordを検証できない（監査 §6）。

**残るBlocking**

- 実装前: Flood用のPublish受入プロファイルと、`candidate_id` とReadiness Recordの対応（OI-28）。ポリシー承認記録のSchema（OI-27）。Flood用の認可プロファイル（OI-17）。
- 公開前: 上記の実装と受入試験。利用条件の解決。OWNERの公開承認。

**OWNER判断事項**: Readiness Recordを新設する契約案の採否。Data Publishとの接続を追加契約として作る方針（OI-28）。

### B7-02 — HIGH：Feature全体の無効性と構成Polygonの利用資格が接続されていない

**指摘の概要**

NはMultiPolygon全体の重なり・辺の共有を評価すると規定していたが、評価行とIntegrationの利用資格は構成Polygon単位で、Feature全体の無効性を引き継ぐ欄がなかった。検索索引はFeature全体の `geometry_sha256` に結び付いていた。そのため、判定可能な構成Polygonだけを検索する対応関係がなかった。合成反例は次の3つである。(1) 内部で重なる有効なPとQの「全体だけ無効」、(2) 有効なPと判定保留のQの混在、(3) 単一の `selection` 値にareaとunknownのどちらを入れるか決まらない。

**修正箇所**: N §9.3.1（新設）、§9.5、§13 N-34・N-35、§14 ON-23、I §4.1（全面改訂）、§4.4、§6.2、§6.3、§7.1、§7.2、§8.1 IV-4・IV-5・IV-14・IV-16・IV-19・IV-23・IV-25、IV-9 (15)〜(17)、§10、§12 I-32〜I-34・I-42、§13 OI-29

**具体的な修正内容**

- 全Featureについて、Feature全体の妥当性（`feature_status`・`feature_level_classes`）、構成Polygonごとの妥当性（`polygon_status`）、Feature全体の無効原因に関与する構成の集合（`feature_invalid_components`）、判定に利用できる構成の集合（`usable_components`）、判定保留の構成の集合（`pending_components`）を別々に記録する（N §9.3.1）。
- 関与する構成は、単体で `valid` でも `pending_components` に入れる。正常な判定に使う規則は、明示的に承認されたポリシーとしてだけ追加できる（ON-23・OI-29）。関与集合を2つの検証器で一致して特定できない場合は、`validation_error` としてAssessmentをFAILEDにする。黙って保守側に倒すことはしない。
- Feature単位の選別を、独立した3つの真偽値 `has_area_match`・`has_unknown`・`has_boundary_touch` で表す。単一の `selection` 列は廃止した（I §4.1・§6.2）。
- 保持の単位は原典Feature（完全保持）、判定の単位は構成Polygonとした。原典Feature全体の形状は `source_geometry` に保持し、検索・判定には使わない。
- 判定に使う形状は、`search_geometry`（構成Polygon単体、または承認された派生形状）と `search_target`（`search_id`・`record_key`・`polygon_index`・`geometry_basis`・`geometry_sha256`）で、明示的に対応付けた。`geometry_rtree` の id は `search_target.search_id` で、`pending_components` の構成や原典Feature全体を登録しない（I §6.2・§6.3）。
- 有効な構成と判定保留の構成が混在する場合も、Pの浸水該当（`search_target`）とQのunknown（`unknown_region`）を両方保持する（IV-19・IV-23）。APIも両方を返す（I §10）。

**反例に対する受入条件**

| 反例 | 受入条件 | テスト |
|---|---|---|
| 内部で重なる有効なPとQ（全体だけ無効） | P・Qとも `pending_components`。構成の `valid` で上書きされず、`search_target` に登録されない | N-34、I-33、IV-14 |
| 有効な島Pと判定保留のQ | Pの `search_target` とQの `unknown_region` が両方存在し、`has_area_match` と `has_unknown` がともに真 | N-35、I-32、IV-9 (15) |
| areaとunknownとtouchが共存するFeature | 3つの真偽値が独立に記録され、情報が失われない | I-34 |
| 索引から原典へ追跡できない | `geometry_rtree` → `search_target` → 原典の構成Polygon・Featureの双方向の追跡が欠けない | IV-25 |
| unknownがあると有効部分の該当が消える | 消えない | I-42 |

**文書上の解決状況**: RESOLVED（文書）。

**アルゴリズム・実装上の未検証事項**

- `feature_invalid_components` を特定する方式（重なり・辺の共有を生じさせた構成の組の検出）と、それを2つの検証器で一致させる方式。妥当性モデルの固定（ON-5）に含まれる。

**残るBlocking**

### B7-03 — HIGH：条件(a)〜(e)だけでは派生出力と原典の数学的解釈の等価性を保証できない

**指摘の概要**

条件(c)は入力の3解釈どうしの一致、条件(d)は3方式の出力どうしの一致であり、「派生出力が(c)で確定した点集合と全域で等しい」ことを直接検証する要件がない。(e)の頂点集合の包含は面の欠落を防がない。調査用のC-3は `shapely.polygonize`・`point_on_surface`・`union_all` に依存しており、GEOSから独立した方式として扱えない。概念上の反例として、共通の欠陥で小さい葉が3方式とも落ちた場合、(a)〜(e)はすべて成立する。また、(a)の検査が列挙する `self_touch_vertex_edge` は同一リング内の定義である。

**修正箇所**: N §10.2（(a)の範囲の明確化、(f)の追加、注記）、§10.4 `conditions`・`status`、§10.5、§10.6、§10.7、§13 N-27・N-33、§14 ON-16・ON-24、I §2.1 6、§8.1 IV-18、§12 I-28・I-41

**具体的な修正内容**

- 現在のC-3がGEOSから独立していると断定しない。`shapely.polygonize`・`shapely.point_on_surface`・`shapely.union_all` への共通依存を明記し、(d)の3方式が共通の欠陥を共有しうると記した。

**文書上の解決状況**: **PARTIALLY RESOLVED（文書）**。要件は文書化したが、要件を満たす独立方式が存在しない。**文書の修正だけでB7-03を完全に解決したとは扱わない。**

### B7-04 — HIGH：L2で消してよいunknownと、残すべき不確実性が分離されていない

**指摘の概要**

契約は、L2へ縮小しても作成者の意図に関する不確実性が残ると認めていた。しかし、L2の格納範囲は解釈差分の領域だけで、縮小後の外側に残る不確実性をAPIへ渡す規則がなかった。3解釈が全域で一致する自己接触形状では差分の領域が空になり、L2の条件と承認が成立するとunknownを空にできる。このとき、派生形状の採用承認がなくても判定保留が消える。

### B7-09 — MEDIUM：L1の包含保証に必要な座標モデル・定義域が不足する

**指摘の概要**

座標の制約はint64に収まることまでで、経緯度の許容範囲が明示されていなかった。RTreeの契約は「地理座標なので `2^53` 未満」を前提にしていた。平面の線分、日付変更線を跨ぐ表現、経度の折り返しを統一する規定もなかった。`2^53+1` はint64に収まるが、float64で厳密に表せない。179°と−179°を跨ぐ形では、min/max矩形による除外の意味が変わる。

**修正箇所**: N §4.2 `coordinate_profile`、§5（拒否条件）、§6.3（初期座標プロファイル）、§8.1 V-13、§13 N-37・N-38、§14 ON-22、I §2.1 4、§3 `parameters.coordinate_profile`、§4.4 手順1、§6.3、§8.1 IV-7 (c)・IV-27、IV-9 (17)、§11.1、§12 I-39

**具体的な修正内容**

- 初期座標プロファイル `coord-profile-geographic-planar-v0.1` を定義した。有限な2次元座標、経度 −180°＜x＜180°（±180°ちょうどは拒否）、緯度 −90°≦y≦90°、データソースごとの許容範囲（値はON-22）、nano-degree整数の範囲（\|x\|＜1.8×10¹¹）、（経度, 緯度）平面上の直線分という解釈、経度のラップなしに限定する。
- 範囲外の座標、経度差が180°を超える辺（日付変更線を跨ぐ表現の可能性）、空の構成（0個の構成・0本のリング・0個の座標）、対応できない構造を、Normalizeで拒否する。黙って処理しない。
- 「int64に収まること」と「float64で厳密に表せること」を区別した。float64として渡してよい根拠は、範囲の検査による `2^53` 未満の保証だけとした。
- RTreeには外向きの包含を要求する。外接矩形の境界上の地点、点状・線状に退化した外接矩形についても、false negativeを禁止した（I §6.3、IV-7 (c)）。
- L1の外接矩形による除外は、境界を含む重なりで判定する。辺・角で接するだけの場合も除外しない（I §4.4）。

**反例に対する受入条件**

| 反例 | 受入条件 | テスト |
|---|---|---|

| 179°と−179°を結ぶ辺 | Normalizeで拒否。Integrationに入らない | N-37、I-39 |
| 空の構成 | 拒否 | N-38 |
| BBoxの辺上・退化したBBoxの地点がunknown検索から漏れる | 候補から漏れない | IV-7 (c)、IV-9 (17)、I-39 |

**文書上の解決状況**: RESOLVED（文書）。

**アルゴリズム・実装上の未検証事項**: SQLiteの版ごとに、退化した矩形と外向きの丸めの実際の挙動を確認すること（IV-7の受入試験）。API入力の座標系・精度（ON-11・OI-18）は本改訂の範囲外で、未決定のまま。
